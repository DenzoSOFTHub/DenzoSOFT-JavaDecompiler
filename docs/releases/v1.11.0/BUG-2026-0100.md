# BUG-2026-0100: try/catch/finally membership decided by source line; all handlers deleted without a LineNumberTable

**Type**: Bug
**Status**: RELEASED
**Severity**: CRITICAL
**Created**: 2026-09-05
**Resolved**: 2026-09-05

## Description
Exception-handler reconstruction decided which statements belong to a `try` region by comparing
SOURCE LINE NUMBERS against the lines of the region's bytecode boundaries. When a class carries no
`LineNumberTable` (javac `-g:none`, and the normal shape of stripped or obfuscated jars) that
comparison cannot run: the group was rejected outright and, because handler blocks are unreachable
from the entry walk, every `catch` body was dropped from the output.

The remaining happy path still compiled, so the loss was silent — the worst defect class for a
decompiler. Measured on the construct matrix at `-g:none`: **0 `catch` clauses survived out of 15
in the source**, and only 1 `finally` of 6.

Example (`C_Exceptions.tryCatchFinally`, `-g:none`, before the fix):

```java
int tryCatchFinally(int[] arg0, int arg1) {
    int var3 = 0;
    var3 = arg0[arg1];
    var3 += 1000;
    return var3;
}
```

The `catch (ArrayIndexOutOfBoundsException e) { result = -1; }` had vanished entirely.

## Technical Analysis
Root cause in `TryCatchReconstructor.applyGroup`:
- `tryStartLine = findLineForPc(tryStartPc, sortedPcs)` followed by `if (tryStartLine < 0) return null;`
  rejected the whole group whenever the region had no line information.
- Membership was `sLine >= tryStartLine && sLine <= tryEndLine`, i.e. a source-line containment test
  standing in for the JVM's own rule, which is a BYTECODE RANGE test on the exception table entry.

Statements only carry a line number (`Statement` is an interface exposing `getLineNumber()` alone),
so no bytecode position was available downstream to classify them.

### Suggested Approach
Record the bytecode pc each statement was decoded at and classify by pc.

### Affected Modules
- `service/converter/ClassFileToJavaSyntaxConverter.java`
- `service/converter/transform/TryCatchReconstructor.java`

### Estimated Effort
MEDIUM-HIGH

## Solution Implemented
An identity map from decoded `Statement` to its bytecode pc is built during block decoding and handed
to the reconstructor, which uses exact bytecode ranges (`pc >= startPc && pc < endPc` — the JVM's own
rule) instead of source lines.

Compound statements built by the flow builder are not themselves in the map, so their position is
computed as the minimum pc of the decoded statements they wrap (`minPcOf`).

The pc criterion is deliberately applied ONLY when the region has no line information
(`tryStartLine < 0`). Switching the classification wholesale also changed grouping for classes that
DO have lines, which regressed try-with-resources collapse (`ModernTwrReconstructor` is tuned against
the established line-based shape — caught by the `TwrT` test). The residual line-based displacement
defect on `-g` code is tracked separately as BUG-2026-0122.

### Files Modified
- `src/main/java/it/denzosoft/javadecompiler/service/converter/ClassFileToJavaSyntaxConverter.java`
  - `statementPcs` identity map field, reset per method
  - every statement emitted by `decodeOpcode` tagged with the pc it was decoded at
  - map handed to the reconstructor next to `setFlowBuilder`
- `src/main/java/it/denzosoft/javadecompiler/service/converter/transform/TryCatchReconstructor.java`
  - `setStatementPcs`, `minPcOf(Statement)` / `minPcOf(List)` / `minOf`
  - `applyGroup` no longer bails when lines are missing; pc-based classification with the line
    logic kept as the fallback path
