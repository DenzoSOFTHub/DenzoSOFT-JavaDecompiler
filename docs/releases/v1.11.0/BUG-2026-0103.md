# BUG-2026-0103: LocalVariableTable scope ranges ignored, so variables sharing a slot collapsed

**Type**: Bug
**Status**: RELEASED
**Severity**: CRITICAL
**Created**: 2026-09-05
**Resolved**: 2026-09-05

## Description
The LocalVariableTable was flattened to one name/descriptor/signature per SLOT, last entry winning;
`start_pc` and `length` were parsed and discarded. When javac assigned two different variables to the
same slot — routine for variables in disjoint scopes — they collapsed into a single identity with one
name and one type, both taken from whichever entry happened to be written last.

The result was wrong names, wrong types, and duplicate declarations. On a `-g` build (Maven/Gradle
default, so essentially every production jar):

```java
String pick(boolean f) {
    Integer count;          // declared twice
    Integer count;
    if (f) {
        count = "yes";      // wrong name AND wrong type
        return count.toUpperCase();
    }
    count = 42;
    return count.toString();
}
```

## Technical Analysis
`ClassFileToJavaSyntaxConverter` builds `localVarNames` / `localVarDescriptors` /
`localVarSignatures` keyed by slot index only. `pushLocal`, `storeLocal` and the pre-declaration scan
then look up by slot, although `currentDecodePc` — the position that identifies WHICH variable is
live — is already tracked for diagnostics.

### Affected Modules
- `service/converter/ClassFileToJavaSyntaxConverter.java`

### Estimated Effort
MEDIUM

## Solution Implemented
The LVT is additionally indexed by slot with each entry's scope `[start_pc, start_pc + length)`, and
`resolveSlotRange(slot, pc)` returns the entry live at a position. A store lands a few bytes before
its variable's `start_pc` (javac opens the scope after the storing instruction), so a near-miss just
ahead of the position counts as belonging to that entry.

**Only slots carrying more than one distinct name are resolved this way.** Every single-entry slot
keeps its previous behaviour exactly, which confines the change to the cases that were actually
broken.

`pushLocal` and `storeLocal` take the name AND the type (signature first, then descriptor) from the
resolved entry. The pre-declaration scan skips shared slots entirely: a single slot-keyed declaration
can only name one of the variables, so `promoteUndeclaredAssignments` gives each distinct name its own
declaration at its first assignment instead.

### Development note
The first, narrower attempt wired only the NAME in `pushLocal`/`storeLocal` and left the
pre-declaration scan and the declaration type alone. Measured on `java.base` it was a **net
regression** (duplicate-declaration files 540 -> 548) with no matrix improvement, because correct
names no longer matched the slot-keyed pre-declaration. Inspecting one regressed file showed the name
resolution itself was right (`defc = getDeclaringClass()` instead of the nonsensical
`ex = getDeclaringClass()`), which identified the pre-declaration scan and the declaration type as the
missing halves rather than the approach being wrong.

### Known residual
This fix is about variable IDENTITY, not about the count of re-declarations: that count is essentially
flat (266 -> 279 sites over 108 files), because correcting a name can expose a pre-declaration that
no longer matches. The remaining re-declarations come from the eager pre-declaration heuristic and are
tracked as BUG-2026-0107 (replace it with the demand-driven hoisting already used by
`BranchVarHoister`/`SwitchVarHoister`).

Wiring only loads and stores was not enough: `iinc` had to be resolved by scope as well, or a loop
counter in a shared slot is incremented under a different name than its loads use, orphaning the
update and preventing `for`-loop reconstruction.
