# BUG-2026-0104: dup2, dup2_x1, dup2_x2, dup_x2 mis-model category-2 (long/double) values

**Type**: Bug
**Status**: RELEASED
**Severity**: HIGH
**Created**: 2026-09-05
**Resolved**: 2026-09-05

## Description
The decompiler's operand stack holds one entry per VALUE, while the JVM counts computational slots —
a `long` or `double` occupies two. The JVMS 6.5 forms of the `dup` family therefore have to be chosen
on the operand's category, which the decoder never did:

- `dup2_x1` (0x5D) and `dup2_x2` (0x5E) were literal no-ops, silently discarding the duplication
- `dup2` (0x5C) always popped two expressions, even when the top of stack was a single category-2 value
- `dup_x2` (0x5B) implemented only form 1, picking its fallback on stack DEPTH rather than category

Consequence: the duplicated value was missing when a later opcode needed it, surfacing as
`STACK_UNDERFLOW` and uncompilable output. `java/util/concurrent/locks/StampedLock.releaseWrite`:

```java
this.state = unlockWriteState(s);
long nextState = null;      // does not compile
```

Where the stack happened to be deep enough the wrong branch was taken silently instead.

## Technical Analysis
Root cause: `ClassFileToJavaSyntaxConverter.decodeOpcode`, cases 0x5B-0x5E. No notion of computational
type category existed in the decoder.

### Affected Modules
- `service/converter/ClassFileToJavaSyntaxConverter.java`

### Estimated Effort
LOW

## Solution Implemented
Added `isCategory2(Expression)` (JVMS 2.11.1: `long` and `double`, detected from the type descriptor)
and implemented every JVMS 6.5 form of `dup_x2`, `dup2`, `dup2_x1` and `dup2_x2`, selecting the form on
category rather than on stack depth. Short-stack cases restore what was popped instead of corrupting
the stack.

A second defect surfaced while verifying the fix: restoring the duplicate made the SAME expression
object appear twice, so `long next = state = f(s)` re-materialized `f(s)` and evaluated it **twice** —
the silent-miscompilation class. The `dup;putfield;store` shape now reuses the aliasing rule already
applied to `dup;store` (BUG-2026-0087): the duplicate left on the stack is replaced by a read of the
field just assigned, so the right-hand side is evaluated once.

### Files Modified
- `src/main/java/it/denzosoft/javadecompiler/service/converter/ClassFileToJavaSyntaxConverter.java`
  - `isCategory2(Expression)` helper
  - full JVMS 6.5 implementation of opcodes 0x5B, 0x5C, 0x5D, 0x5E
  - `putfield` aliases the duplicate to a field read instead of re-materializing the value

### Test Case
- Test class: `DecompilerTest`
- Test method: `testCategory2Dup`
- Verifies: `long next = state = s + 1L;`, `double v = a[i] = 3.0;` and `(nanos = deadline - now) <= 0L`
  decompile with no `= null` and no `STACK_UNDERFLOW` (fails on the pre-fix build)

### Measured Result
| Gate | Before | After |
|---|---|---|
| `java.base` files with STACK_UNDERFLOW | 16 | **7** |
| `java.base` uncompilable `long/double x = null;` | 1 | **0** |
| Construct matrix (all three debug modes) | 55/53/53 | 55/53/54 (no regression) |

### Known residual
`state = f()` on a **volatile** field is rendered as `state = f(); x = state;`, which re-reads the
volatile rather than reusing the assigned value as `x = state = f()` would. Correct for ordinary
fields; a chained-assignment rendering would be needed to be exact under concurrency.
