# BUG-2026-0101: synchronized region nested inside any compound statement silently dropped

**Type**: Bug
**Status**: RELEASED
**Severity**: CRITICAL
**Created**: 2026-09-05
**Resolved**: 2026-09-05

## Description
`synchronized` reconstruction ran only over the top-level statement list of a method. A monitor
region nested inside an `if`, loop, `try`, `switch` or label was never reconstructed: the output kept
the internal marker comments and the synthetic try/finally, and the lock silently disappeared while
the body still compiled.

Before the fix:

```java
if (f) {
    try {
        Object var2 = this.lock;
        /* __MONITORENTER__ */
    } finally {
        /* __MONITOREXIT__ */
    }
    this.counter += 1;
    /* __MONITOREXIT__ */
}
```

The mutation executes OUTSIDE any lock — a concurrency-semantics change that no compiler would flag.
Measured on JDK 25 `java.base`: **98 of 3,376 decompiled classes** carried a leaked
`__MONITORENTER__` marker (`java/util/Date`, `String`, `ConcurrentHashMap`, `WeakHashMap`, `Pattern`,
`ResourceBundle`, ...).

## Technical Analysis
`reconstructSynchronized` walked only the list it was given, and its helper
`stripMonitorFromTryFinally` recursed into `BlockStatement` only. Neither descended into
`If`/`IfElse`/`While`/`DoWhile`/`For`/`ForEach`/`Try`/`Switch`/`Label`/`Synchronized` bodies, while the
monitor try/finally itself is built by `TryCatchReconstructor` inside the enclosing structure.

### Suggested Approach
Recurse into every compound body, mirroring `BranchVarHoister.recurse`.

### Affected Modules
- `service/converter/ClassFileToJavaSyntaxConverter.java`

### Estimated Effort
LOW

## Solution Implemented
Added `recurseSynchronized(Statement)` and `rebuildSynchronizedBody(List)`, which rewrite each nested
body in place (the reconstruction returns a new list, so the body's contents are replaced).

Ordering is the subtle part and was found by testing: the recursion must run **after** the current
list has consumed its own `__MONITORENTER__`/`__MONITOREXIT__` pair. Descending first eats the
`__MONITOREXIT__` inside an enclosing region's try-body, leaving that region with no end — which
produced an empty `synchronized {}` with the body hoisted OUT of the lock, a worse defect than the
original. With the correct ordering, any marker still present in a nested body provably belongs to
that body, so nested bodies get exactly the same treatment as the top-level list.

### Files Modified
- `src/main/java/it/denzosoft/javadecompiler/service/converter/ClassFileToJavaSyntaxConverter.java`
  - `reconstructSynchronized`: descends into a single-statement list; recursion moved to after the
    marker-pairing loop
  - new `recurseSynchronized(Statement)` / `rebuildSynchronizedBody(List)`

### Test Case
- Test class: `DecompilerTest`
- Test method: `testNestedSynchronized`
- Verifies: `synchronized` inside an `if` and inside a `for` are both reconstructed, and no
  `__MONITORENTER__` / `__MONITOREXIT__` marker leaks (fails on the pre-fix build)

### Measured Result
| Gate | Before | After |
|---|---|---|
| `java.base` classes with a leaked `__MONITORENTER__` | 98 | **0** |
| `java.base` reconstructed `synchronized (` blocks | 720 | **932** (+212) |
| `java.base` decompile errors | 0 | 0 |

### Known residual
A `synchronized` nested in an `if` whose branch continues with further statements can still lose the
method's trailing `return` — a pre-existing defect of that shape, unrelated to monitors and present
before this fix. Tracked as BUG-2026-0121.
