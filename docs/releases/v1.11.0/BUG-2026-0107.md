# BUG-2026-0107: the same local declared twice in one scope (uncompilable)

**Type**: Bug
**Status**: RELEASED
**Severity**: HIGH
**Created**: 2026-09-05
**Resolved**: 2026-09-06

## Description
Java forbids declaring a local whose name is already in scope, but the decoder identifies locals by
bytecode slot. When javac reuses one slot for two same-named variables in disjoint source scopes —
two consecutive `for (int i = ...)` loops being the everyday case — and the loop reconstruction hoists
each declaration out of its for-header, the output declared the same name twice in one block and did
not compile.

Two loops over two arrays produced four declarations for two variables:

```java
int total;
int i;
int total = 0;   // error: variable total is already defined
int i = 0;       // error: variable i is already defined
```

Measured on JDK 25 `java.base`: **1,120 files / 8,055 sites** on the v1.10.0 build.

## Technical Analysis
Two independent mechanisms each emit a declaration for the same slot: the LVT-driven pre-declaration
scan, and the promotion of an otherwise-undeclared assignment. BUG-2026-0106 removed the case where
both fire for a single variable; what remained is genuine slot REUSE, where two distinct source
variables legitimately map to one slot and each needs its own declaration point — but they end up in
the same emitted block.

### Suggested Approach
A late pass over the final statement tree, after all structural transforms have settled the block
shape.

### Affected Modules
- `service/converter/transform/` (new pass)
- `service/converter/ClassFileToJavaSyntaxConverter.java` (wiring)

### Estimated Effort
LOW-MEDIUM

## Solution Implemented
New transform `DuplicateDeclarationDemoter`, run last in both flow paths (legacy and JD), just before
`mergeDeclarationsWithAssignments`. It walks the statement tree with a scope stack that mirrors Java's
own scoping rules — `for` and for-each headers, try resources, each catch clause, and a switch's cases
sharing one scope — and, when a declaration's name is already declared in an enclosing or current
scope **with the same type**, rewrites it as a plain assignment (or drops it when it has no
initializer).

A re-declaration with a DIFFERENT type is deliberately left alone: that is a genuinely distinct
variable needing a fresh name, and merging it would change the program. 106 of the 128 residual sites
measured before this fix were same-type; the 22 different-type ones remain.

### Measurement note
These counts come from a scope-aware scanner (brace depth, keyword exclusion, fields separated from
locals, `} else {` closing before opening). Two earlier drafts of the figure used looser heuristics
that matched `return x;` as a declaration and paired lines across different methods; the numbers here
supersede those. The residual 15 files still include cross-method false positives (the scanner counts
braces inside string literals), so 28 is an upper bound.
