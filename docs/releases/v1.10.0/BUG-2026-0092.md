# BUG-2026-0092: Nested synchronized flattened (enter/exit pairing) + static synchronized modifier dropped

**Type**: Bug
**Status**: CLOSED (v1.10.0)
**Severity**: HIGH
**Created**: 2026-06-10
**Resolved**: 2026-06-10
**Cluster**: `synchronized-reconstruction` (construct-matrix gap analysis, fix order #12)
**Parent/related**: BUG-2026-0080 (umbrella, 'return-across-synchronized'); NEW dedicated item — umbrella BUG-2026-0080

## Description

Class of defect: decompile→recompile failure. Matrix classes affected: C_Concurrency.

- **C_Concurrency**: Nested synchronized is flattened and its body misplaced: source `synchronized(this){ synchronized(lock){ return counter+cache; } }` decompiles to `synchronized (this) { Object var2 = this.lock; }` — the inner synchronized(this.lock) block disappears, its lock-temp declaration is left behind as dead code, and (once the dropped return is restored by the finally-dedup fix) the `return` lands AFTER both monitors instead of inside them.
- **C_Concurrency**: Not a javac error, but wrong output: `public static synchronized void staticSync()` (method access flags 0x29 = ACC_PUBLIC|ACC_STATIC|ACC_SYNCHRONIZED, confirmed via javap) is decompiled as `public static void staticSync()` — the `synchronized` modifier is silently dropped on static methods, changing locking semantics on recompile. Instance synchronized methods are emitted correctly.

## Technical Analysis

### C_Concurrency (confidence: HIGH)

reconstructSynchronized in src/main/java/it/denzosoft/javadecompiler/service/converter/ClassFileToJavaSyntaxConverter.java:3496-3561 cannot represent nesting: while collecting the body of an outer __MONITORENTER__ it SKIPS any nested __MONITORENTER__ marker (:3536-3539, 'Skip nested monitor markers') instead of recursing, and terminates the body at the FIRST __MONITOREXIT__ (:3533) — i.e. it pairs the outermost enter with the innermost exit. For nestedSynchronized the post-trycatch marker sequence is [Decl var1=this, ENTER, Decl var2=this.lock, ENTER, EXIT, EXIT(, Return)] (confirmed via instrumented dump); the loop consumes `Decl var2=this.lock` as body, drops the inner ENTER, stops at the inner EXIT, and the second EXIT is discarded at :3555-3557, so no inner SynchronizedStatement is ever built and the inner lock decl survives as junk.

### C_Concurrency (confidence: HIGH)

src/main/java/it/denzosoft/javadecompiler/service/writer/JavaSourceWriter.java:1457 explicitly suppresses the keyword for static methods: `if ((accessFlags & StringConstants.ACC_SYNCHRONIZED) != 0 && (accessFlags & StringConstants.ACC_STATIC) == 0)`. The `&& !static` conjunct has no JLS basis — `static synchronized` is legal Java (the monitor is the Class object). It was presumably added defensively because 0x0020 doubles as ACC_SUPER on classes, but the enclosing `!isClass` guard (:1456) already excludes classes, and fields cannot carry 0x0020 per JVMS 4.5.

### Suggested Approach

(1) ClassFileToJavaSyntaxConverter.reconstructSynchronized (:3496-3561) pairs the outermost __MONITORENTER__ with the FIRST __MONITOREXIT__ and skips nested ENTERs (:3533-3539) — rewrite as balanced-parentheses pairing (recurse on nested ENTER, consume the preceding lock-temp declaration as inner monitor expression, terminate at the depth-matched EXIT), and move a Return/Throw immediately following the final EXIT inside the innermost body. (2) One-liner: JavaSourceWriter.java:1457 — delete the '(accessFlags & ACC_STATIC) == 0' conjunct so 'static synchronized' is emitted (legal Java; the !isClass guard already excludes ACC_SUPER ambiguity). Together with finally-dedup this unblocks C_Concurrency.

Per-finding fix details:

- Rewrite the marker pairing in reconstructSynchronized (ClassFileToJavaSyntaxConverter.java:3529-3553) to treat __MONITORENTER__/__MONITOREXIT__ as balanced parentheses: on encountering a nested ENTER while collecting a body, recurse (or use an explicit depth/stack) to build an inner SynchronizedStatement, consuming the immediately preceding lock declaration (e.g. `Object var2 = this.lock`) as the inner monitor expression and removing it from the body — same lock-extraction logic already present at :3506-3527. The outer body must terminate at its own depth-matched EXIT, not the first one seen. Additionally, when a Return/Throw immediately follows the final EXIT of a region (its value was computed inside the monitor before monitorexit), move it inside the innermost reconstructed body so the source-level semantics (return under the lock) are preserved.

- In JavaSourceWriter.java:1457 delete the `(accessFlags & StringConstants.ACC_STATIC) == 0` conjunct so the keyword is emitted for any non-class, non-field member with ACC_SYNCHRONIZED set (guard with !isField if needed — the isField parameter is already in scope at :1466). One-line change; add a `static synchronized` method to the round-trip test corpus.

## Solution Implemented

Changes tagged `BUG-2026-0092-20260610-1` (converter) and `BUG-2026-0092-20260610-2` (writer).

1. **Balanced monitor-marker pairing** (`reconstructSynchronized`, tag -1): the linear
   scan that paired the outermost `__MONITORENTER__` with the FIRST `__MONITOREXIT__`
   (skipping nested enters) was replaced by recursive balanced-parentheses pairing:
   - `extractLockFromTail(List<Statement>)` — factored lock-expression extraction
     (dup+astore pattern: trailing `varX = lockExpr` declaration/assignment is consumed
     as the monitor expression and removed from the collected list). Used both at the
     top level (on `result`) and for nested enters (on the partially collected body).
   - `collectSynchronizedRegion(cleaned, pos, lockExpr)` — collects a region's body
     starting just after its ENTER; a nested ENTER recurses (building an inner
     `SynchronizedStatement` whose lock comes from the preceding lock-temp declaration);
     the region terminates at its own depth-matched EXIT. An unpaired nested ENTER with
     no preceding lock-temp is dropped (legacy behavior).
   - **Return/Throw hoisting** (`hoistTailIntoSync`): a Return-with-value or Throw
     immediately following a region's closing EXIT had its value computed under the
     lock (carried across `monitorexit` on the operand stack), so it is moved into the
     innermost reconstructed body (descending through a trailing chain of nested
     SynchronizedStatements; aborted if the innermost body already ends abruptly, which
     would create unreachable code). Applied at BOTH the top level (shape
     `[ENTER ... EXIT, Return]`) and after a nested region inside
     `collectSynchronizedRegion` (shape `[ENTER1, Decl2, ENTER2 ... EXIT2, Return]` —
     the outer EXIT is often already stripped by the try-finally unwrap, confirmed via
     instrumented dump: nestedSynchronized arrives as
     `[Decl var1=this, ENTER, Decl var2=this.lock, ENTER, EXIT, Return]`).
     Bare `return;` (no expression) is never hoisted.
2. **`static synchronized` emission** (JavaSourceWriter, tag -2): deleted the
   `(accessFlags & ACC_STATIC) == 0` conjunct from the ACC_SYNCHRONIZED check.
   `static synchronized` is legal Java (monitor is the Class object); the enclosing
   `!isClass` guard already excludes the ACC_SUPER (0x0020) ambiguity on classes, and
   fields cannot carry 0x0020 per JVMS 4.5.
