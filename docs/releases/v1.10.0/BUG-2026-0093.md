# BUG-2026-0093: CastExpression operand printed without precedence parentheses ((T) ternary mis-parses)

**Type**: Bug
**Status**: RELEASED (v1.10.0)
**Severity**: HIGH
**Created**: 2026-06-10
**Resolved**: 2026-06-10
**Cluster**: `cast-precedence` (construct-matrix gap analysis, fix order #13)
**Parent/related**: NEW (sibling of released BUG-2026-0052) — umbrella BUG-2026-0080

## Description

Class of defect: decompile→recompile failure. Matrix classes affected: C_Generics, C_RecursiveGenerics.

- **C_Generics**: javac: "/tmp/matrix/dec/C_Generics.java:36: error: incompatible types: int cannot be converted to U" on `return (U) ((Comparable) arg0).compareTo(arg1) >= 0 ? arg0 : arg1;` (decompiled from `<U extends Number & Comparable<U>> U max(U,U)`).
- **C_RecursiveGenerics**: 2 javac errors: "incompatible types: int cannot be converted to T" at dec lines 6 and 10, from `return (T) arg0.compareTo(arg1) >= 0 ? arg0 : arg1;` in maxOf and the analogous `<= 0` line in minOf. The (T) cast binds to the int result of compareTo instead of the whole ternary.

## Technical Analysis

### C_Generics (confidence: HIGH)

Cast printed without parenthesizing a lower-precedence operand. ClassFileToJavaSyntaxConverter.java:430-443 detects the type-variable return type `U` from the method signature and addGenericReturnCasts (ClassFileToJavaSyntaxConverter.java:789-822, specifically 801-802) wraps the whole return TernaryExpression in CastExpression(GenericType("U"), ternary). JavaSourceWriter.java:2806-2836 then renders CastExpression as `(U) ` + operand with NO parentheses around the operand (lines 2832-2835), and generic-type casts are never suppressed as redundant (lines 2813-2816). Since a cast binds at unary precedence (JLS 15.16), the emitted text re-parses as `((U) ((Comparable) arg0).compareTo(arg1)) >= 0 ? arg0 : arg1`, casting the int compareTo result to U. The TernaryExpression writer branch (JavaSourceWriter.java:2919-2925) likewise emits no self-parens, so any CastExpression (also checkcast at ClassFileToJavaSyntaxConverter.java:2764 and primitive conversion at :3150) over a ternary/binary/assignment/instanceof operand has the same latent bug. NOTE: this refutes the erasure-generics hypothesis as the cause of the compile failure for this class — the erased raw `ArrayList var1 = new ArrayList()` / `new HashMap()` locals (no LVTT) only produce unchecked warnings, not errors.

**Verifier correction**: Two immaterial nits: cited paths omit package prefixes (actual files are src/main/java/it/denzosoft/javadecompiler/service/converter/ClassFileToJavaSyntaxConverter.java and .../service/writer/JavaSourceWriter.java), and LambdaExpression after a reference-type cast is grammatically legal without parens (JLS CastExpression production), so including it in the paren set is harmless but not strictly required.

### C_RecursiveGenerics (confidence: HIGH)

Two-stage mechanism. (1) ClassFileToJavaSyntaxConverter.addGenericReturnCasts (src/main/java/it/denzosoft/javadecompiler/service/converter/ClassFileToJavaSyntaxConverter.java:789-803, BUG-2026-0031 change) wraps EVERY non-cast, non-null return expression in CastExpression(genType, expr) when the method signature's return type is a type variable (here `<T::Ljava/lang/Comparable<TT;>;>(TT;TT;)TT;`). The wrapped expression is the TernaryExpression `arg0.compareTo(arg1) >= 0 ? arg0 : arg1`. (2) JavaSourceWriter's CastExpression branch (src/main/java/it/denzosoft/javadecompiler/service/writer/JavaSourceWriter.java:2806-2836) prints `(T) ` then writes the operand with no parentheses (lines 2832-2835), regardless of operand precedence. Since a cast binds tighter than `>=` and `?:`, javac parses `((T) arg0.compareTo(arg1)) >= 0 ? ...`. Note the cast is also semantically unnecessary here: both ternary branches are parameters already declared as T. The redundant-cast suppression at writer:2813-2816 deliberately never suppresses casts to GenericType, so the broken text is always emitted. Not an erasure/LVTT data-loss issue — purely an emission bug.

**Verifier correction**: Minor citation drift only: the needsParentheses helper is at JavaSourceWriter.java:3332 (its BUG-2026-0013-2 END_CHANGE tag is at line 3358), not 'near line 3239'. The helper exists, is BUG-2026-0013-tagged, and currently only handles BinaryOperatorExpression/AssignmentExpression children of binary operators, so the proposed extension to cast operands is the right shape.

### Suggested Approach

JavaSourceWriter CastExpression branch (:2831-2836): wrap the operand in '(...)' when it is a TernaryExpression, BinaryOperatorExpression, AssignmentExpression, or InstanceOfExpression (below unary precedence), extending the existing needsParentheses idiom (:3332, BUG-2026-0013). Fixes 'return (U) cmp >= 0 ? a : b' in C_Generics.max and both C_RecursiveGenerics maxOf/minOf errors (verified by hand-edit). Optional polish: ClassFileToJavaSyntaxConverter.addGenericReturnCasts (:789-822) skip the cast when the return is a ternary over locals already typed as the type variable.

Per-finding fix details:

- In JavaSourceWriter.writeExpression, CastExpression branch (JavaSourceWriter.java:2831-2836): before writing the operand, compute `boolean operandNeedsParens = operand instanceof TernaryExpression || operand instanceof BinaryOperatorExpression || operand instanceof AssignmentExpression || operand instanceof InstanceOfExpression || operand instanceof LambdaExpression` (anything below unary precedence) and wrap the operand in '(' ')' when true. Verified manually: rewriting the line to `return (U) (((Comparable) arg0).compareTo(arg1) >= 0 ? arg0 : arg1);` compiles with zero errors. Optional quality follow-up (not required for the error): addGenericReturnCasts (ClassFileToJavaSyntaxConverter.java:789) could skip wrapping when the return expression is a TernaryExpression whose branches are parameters/locals already typed as the generic type variable, avoiding the unnecessary unchecked cast altogether.

- Primary fix in JavaSourceWriter.java CastExpression branch (~line 2831-2836): before writing the operand of a non-redundant cast, parenthesize it when its precedence is lower than unary/cast level — i.e. when ce.getExpression() is a TernaryExpression, BinaryOperatorExpression, AssignmentExpression, or InstanceOfExpression: print "(", writeExpression, ")". This mirrors the existing precedence handling for binary operands (needsParentheses helper near JavaSourceWriter.java:3239, BUG-2026-0013) and fixes the general class of `(Type) a OP b` mis-emissions, not just ternaries. Optional polish in ClassFileToJavaSyntaxConverter.addGenericReturnCasts (line 793-803): skip the cast when the return expression is a local/parameter (or a ternary whose both branches are locals) whose declared type already equals the type-variable, eliminating the redundant `(T) (...)` entirely. Verified: adding parens around both ternaries plus the finding-2 fix makes the decompiled file compile with zero errors.

## Solution Implemented

In the non-redundant CastExpression branch of `JavaSourceWriter.writeExpression`, the cast operand
is now wrapped in `( ... )` when it is a `TernaryExpression`, `BinaryOperatorExpression`,
`AssignmentExpression`, or `InstanceOfExpression` — i.e. anything that binds below unary/cast
precedence (JLS 15.16). This extends the existing `needsParentheses` precedence idiom
(BUG-2026-0013). LambdaExpression was deliberately left out: a lambda is grammatically legal
directly after a reference-type cast (verifier note in the analysis above), and C_Lambdas output
is unchanged.

### Files Modified

- `src/main/java/it/denzosoft/javadecompiler/service/writer/JavaSourceWriter.java` —
  `// START_CHANGE: BUG-2026-0093-20260610-1` in the CastExpression writer branch:
  computes `operandNeedsParens` and emits `(operand)` for below-unary-precedence operands.
