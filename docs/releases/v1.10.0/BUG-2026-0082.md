# BUG-2026-0082: iinc decoded as standalone statement — post-increment value semantics lost

**Type**: Bug
**Status**: CLOSED (v1.10.0)
**Severity**: CRITICAL
**Created**: 2026-06-10
**Resolved**: 2026-06-10
**Cluster**: `iinc-postfix-expression` (construct-matrix gap analysis, fix order #2)
**Parent/related**: NEW — umbrella BUG-2026-0080

## Description

Class of defect: SILENT MISCOMPILATION (recompiles cleanly, computes wrong values). Matrix classes affected: C_Operators.

- **[CRITICAL] C_Operators**: Post-increment in return position returns the wrong value. Original 'return a++;' must return the OLD value (bytecode: iload_1; iinc 1,1; ireturn), but the decompiled code increments first and then returns, yielding the NEW value. Runtime proof: postIncrement(5) returns 5 in the original, 6 in the recompiled decompiled output.
  - original: `int postIncrement(int a) { return a++; }`
  - decompiled: `int postIncrement(int arg0) {
    arg0++;
    return arg0;
}`
- **[CRITICAL] C_Operators**: Post-decrement in return position returns the wrong value, same defect as postIncrement. Original 'return a--;' returns the OLD value; decompiled output decrements first and returns the new value. Runtime proof: postDecrement(5) returns 5 in the original, 4 in the recompiled decompiled output.
  - original: `int postDecrement(int a) { return a--; }`
  - decompiled: `int postDecrement(int arg0) {
    arg0--;
    return arg0;
}`
- **[CRITICAL] C_Operators**: Mixed pre/post increment inside an expression is hoisted incorrectly: 'int r = a++ + ++a;' evaluates to a + (a+2) = 2a+2 (the left operand is the pre-increment value, per bytecode iload_1; iinc; iinc; iload_1; iadd). The decompiled code performs both increments before the addition, computing (a+2)+(a+2) = 2a+4. Runtime proof: incInExpression(5) returns 12 in the original, 14 in the recompiled decompiled output.
  - original: `int incInExpression(int a) {
    int r = a++ + ++a;
    return r;
}`
  - decompiled: `int incInExpression(int arg0) {
    arg0++;
    arg0++;
    int var2 = arg0 + arg0;
    return var2;
}`

## Technical Analysis

Root cause documented in the verified semantic-divergence audit (see report-construct-matrix-gap-analysis.md). The mechanism lives in the modules listed below.

### Suggested Approach

case 0x84 in ClassFileToJavaSyntaxConverter.java (:2024-2041) always emits 'var++;' as an ExpressionStatement, ignoring the operand stack. Fix: (1) if the stack holds a LocalVariableExpression alias of the same slot (iload preceded iinc), replace that stack entry with UnaryOperatorExpression postfix 'var++/var--' instead of emitting a statement (restores 'return a++'); (2) otherwise record a pending iinc for the slot and fuse it as prefix '++var' into the NEXT iload of that slot within the same decode run, flushing as a statement at block/statement boundaries (restores 'a++ + ++a'). For-loop increment detection is unaffected because the stack is empty at loop-tail iinc. Share the helper with the wide-iinc fix (cluster wide-opcode-decode).

## Solution Implemented

`iinc` decoding was extracted into a shared helper `decodeIinc(varIdx, incr, stack, statements,
localVarNames, line)` (also used by the BUG-2026-0084 wide-iinc fix) implementing exactly the
suggested approach:

- **(a) postfix**: if the operand-stack TOP is a `LocalVariableExpression` of the same slot
  (javac pattern `iload; iinc +-1`), it is replaced in place with a postfix
  `UnaryOperatorExpression` `var++`/`var--` instead of emitting a statement. This is always
  semantically faithful: the old value stays as the expression value, the variable is bumped.
- **(b) prefix fusion**: otherwise, for +-1 increments, a pending iinc is recorded
  (`pendingIinc*` fields). At the start of the NEXT `decodeOpcode` call it fuses as prefix
  `++var`/`--var` if and only if that next opcode is an `iload`/`iload_0..3` of the same slot
  (javac pattern `iinc; iload`); for ANY other opcode it is flushed as the previous `var++;`
  statement form. The fusion window is therefore exactly one instruction — conservative per
  the analysis. Pending state is additionally reset at the start and flushed at the end of
  every decode run (`decodeBasicBlock` and `decompileMethodBodyLinear`), so it never crosses a
  basic-block or method boundary.
- **(c) non-unit increments** keep the previous `var += N;` statement emission (javac never
  leaves a value-carrying load of the slot on the stack for those).

For-loop tail increments are unaffected (stack empty, the increment is the last instruction of
its block, so the pending iinc flushes to the same `var++;` statement as before) — verified:
`for (...)` reconstruction intact in C_ControlFlow/C_EnhancedFor/C_Arrays. One benign style
change: a do-while whose body ends `n--;` directly before the condition now renders the fused
form `} while (--n > 0)` — runtime-proven equivalent (see Test Case).

### Test Case
- Matrix round-trip C_Operators (runtime proof, 2026-06-10, build `/tmp/dc-wave1a`): decompiled
  source now reads `return arg0++;`, `return arg0--;`, `return ++arg0;`, `return --arg0;`,
  `int var2 = arg0++ + ++arg0;`. Recompiled with JDK 25 and compared against the original class:
  `postIncrement(5)=5`, `postDecrement(5)=5`, `incInExpression(5)=12`, `preIncrement(5)=6`,
  `preDecrement(5)=4` — identical on both (previously 6, 4, 14).
- Do-while regression (minimal `count++; n--; } while (n>0)` class): decompiles to the fused
  `} while (--arg0 > 0)` form; original vs recompiled outputs identical for n in [-2..5].
- For-loop regression: C_EnhancedFor / C_ControlFlow / C_Arrays still reconstruct `for (...)`
  headers with `var++` updates and recompile with 0 errors.
- Full matrix regression: 41/57 clean vs 37/57 baseline; no new failures. DecompilerTest 32/33,
  exact parity with baseline (the 1 failure is the pre-existing stale `super()` expectation in
  BasicClass, present on the unmodified build as well).
