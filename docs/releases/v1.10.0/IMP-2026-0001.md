# IMP-2026-0001: Inner classes should be positioned at original line number location

**Type**: Improvement
**Status**: RELEASED (v1.10.0)
**Severity**: LOW
**Created**: 2026-03-24
**Resolved**: 2026-06-10

## Description
Inner classes should be positioned at original line number location

## Technical Analysis
The default CLI mode is line-aligned: `Main.StringPrinter.startLine(int)` pads blank lines
forward so each construct lands on its original source line (taken from the
`LineNumberTable`). Padding is forward-only — the printer can never go back to an earlier
line.

`JavaSourceWriter` emitted all named inner classes in a fixed position: after every
method of the enclosing type, in `InnerClasses`-attribute order (top-level loop in
`writeCompilationUnit`, nested loop in `writeInnerClass`). Consequences in aligned mode:

- A nested type whose methods sit on early source lines (e.g. `C_InnerClasses.StaticNested`
  declared at line 8) was emitted after the outer methods, ending up 40-70 lines past its
  original location with no possibility of alignment (forward-only padding).
- Worse, the missing early lines were "absorbed" as giant blank-line pads inside the FIRST
  outer method emitted after the inner classes' original line range (19 consecutive blank
  lines inside `makeInner` in the baseline output of `C_InnerClasses`).

### Suggested Approach
Compute a source-line anchor per inner class (minimum `LineNumberTable` line across its
methods, recursing into nested types) and per outer method (minimum line across its body
statements). Emit inner classes interleaved with the outer methods in ascending anchor
order. Conservative fallbacks: fields stay first as today; methods keep their relative
order; inner classes without line info (e.g. `-g:none`) keep their current order and
position (after the methods), making the output byte-identical when no line signal exists.

### Affected Modules
- `service/writer/JavaSourceWriter.java` (only)

### Estimated Effort
LOW

## Solution Implemented
Anchor-based interleaving in `JavaSourceWriter`, applied to both the top-level member loop
(`writeCompilationUnit`) and the nested-type loop (`writeInnerClass`):

1. **Anchor computation** (`statementAnchorLine`, `methodAnchorLine`,
   `innerClassAnchorLine`): minimum positive source line across a method body's statements
   (recursing into blocks); a type's anchor is the minimum across its methods and nested
   types. 0 = no line info.
2. **Ordering** (`orderInnerClassesByAnchor`): inner classes queued sorted by anchor with a
   stable sort; anchor-0 entries sort last keeping their previous relative order. Anonymous
   classes (numeric simple name; inlined at use sites per BUG-2026-0029/BUG-2026-0038) are
   excluded at the top level (matching the old skip-before-blank-line behavior) and kept
   with anchor 0 in the nested loop (matching the old blank-line + early-return behavior).
3. **Interleaving** (`flushPendingInnerClasses`): before emitting each method, all queued
   inner classes whose anchor precedes the method's anchor are emitted (each with its
   separator blank line); the remainder (no line info, or anchored after the last method)
   is emitted where the old single loop ran. The `firstVisibleMethod` /
   `innerFirstMethod` flag is cleared when a flush emitted something so separator blank
   lines stay consistent.

The change is writer-only and ordering-only: no statement rendering changes. Member order
is semantically irrelevant in Java, so recompilation behavior is unaffected.

### Files Modified
- `src/main/java/it/denzosoft/javadecompiler/service/writer/JavaSourceWriter.java` —

### Before/after positioning evidence (line-aligned mode)

`C_InnerClasses` (original: `StaticNested` at line 8, `MemberInner` at 19, `makeInner`
body at 29-31):

| Construct | Original line | Before | After |
|---|---|---|---|
| `static class StaticNested` | 8 | 88 | 9 |
| `class MemberInner` | 19 | 64 | 21 |
| `makeInner` body | 30 | 30 (after 19 blank pad lines inside the method) | 34 (no pad block) |

`C_Sealed` (original: `record Lit` at 9, `class Neg` at 17 with ctor body line 21,
`class Wild` at 30, `class Shape` at 44): before, ALL nested types were emitted after
`evalArea` (which carried a 55-line pad block); after, `Lit` -> line 5, `Neg` -> 11 with
`this.operand = arg0;` landing exactly on original line 21, `Wild` -> 29, `Shape` -> 48.

`service/converter/JavaSyntaxResult.class` (own code): nested class emission order changed
from attribute order (`InnerClassInfo, RecordComponentInfo, MethodDeclaration,
FieldDeclaration`) to original source order (`FieldDeclaration` line 142,
`MethodDeclaration` 179, `RecordComponentInfo` 245, `InnerClassInfo` 266).

Second-level nesting verified: a nested class `A` containing `a1()`, `static class A1`,
`a2()` (in that source order) now emits `A1` between `a1` and `a2`, and recompiles.
