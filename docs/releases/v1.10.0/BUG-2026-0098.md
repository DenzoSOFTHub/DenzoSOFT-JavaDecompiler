**Type**: Bug

**Created**: 2026-06-10

## Description

Class of defect: decompile→recompile failure. Matrix classes affected: C_FunctionalInterfaces, C_Optional.


## Technical Analysis

### C_FunctionalInterfaces (confidence: HIGH)

**Symptom**: Not a compile error (compiles with unchecked warning), but wrong/extra output: useConsumer() decompiles to `Objects.requireNonNull(System.out); Consumer var1 = System.out::println;` — the original source line 59 is just `Consumer<String> printer = System.out::println;`. The compiler-synthesized null check leaks as a standalone statement, and the raw `Consumer` type is the same erasure defect as finding 1.

javac compiles a bound instance method reference as `getstatic System.out; dup; invokestatic java/util/Objects.requireNonNull:(Ljava/lang/Object;)Ljava/lang/Object;; pop; invokedynamic #5:accept:(Ljava/io/PrintStream;)Ljava/util/function/Consumer;` (verified via javap on /tmp/matrix/cls/C_FunctionalInterfaces.class) — an implicit null check of the captured receiver. The converter renders the dup/invokestatic/pop sequence as an ExpressionStatement `Objects.requireNonNull(System.out);`; the bound method-reference branch (ClassFileToJavaSyntaxConverter.java:2639-2651, BUG-2026-0074) then correctly emits `System.out::println` from the captured arg, but nothing recognizes and suppresses the preceding synthetic null-check statement. grep confirms no requireNonNull suppression logic exists anywhere in the decompiler source.

**Fix detail**: In ClassFileToJavaSyntaxConverter.java, in the method-reference branch of case 0xBA (around lines 2639-2651): when a boundReceiver is captured, inspect the tail of `statements` — if the last statement is an ExpressionStatement wrapping a StaticMethodInvocationExpression of java/util/Objects.requireNonNull whose single argument is structurally equal to the captured receiver expression (same field access / local), remove that statement before pushing the MethodReferenceExpression. Alternatively implement it as a peephole in a transform pass (e.g. a small rule alongside BooleanSimplifier) that deletes `Objects.requireNonNull(x);` statements immediately preceding a statement whose expression tree contains a MethodReferenceExpression bound to x. Guard on the exact owner/name/descriptor (java/util/Objects.requireNonNull:(Ljava/lang/Object;)Ljava/lang/Object;) so user-written requireNonNull calls (whose result is used, or not followed by a matching bound method ref) are preserved.

### C_Optional (confidence: HIGH)

**Symptom**: Cosmetic (compiles, semantics preserved): decompiled ifPresentPrint emits an extra statement 'Objects.requireNonNull(System.out);' before 'Optional.ofNullable(arg0).ifPresent(System.out::println);' that does not exist in the original source.

javac compiles the bound method reference 'System.out::println' with a receiver null-check idiom: 'getstatic System.out; dup; invokestatic java/util/Objects.requireNonNull; pop' (confirmed via javap, ifPresentPrint offsets 4-11). In ClassFileToJavaSyntaxConverter: dup (line 1931-1933) duplicates the getstatic expression, invokestatic (lines 2335-2366) pushes the requireNonNull call, and the pop handler at case 0x57 (lines 1907-1919) sees a StaticMethodInvocationExpression and unconditionally materializes it as an ExpressionStatement (lines 1911-1915). No peephole recognizes the requireNonNull-on-dup'd-receiver idiom, while the method reference itself is correctly reconstructed (BUG-2026-0074 bound-receiver path at lines 2639-2650).

**Fix detail**: In the case 0x57 pop handler (ClassFileToJavaSyntaxConverter.java:1907-1919), before emitting the statement, check: popped is a StaticMethodInvocationExpression of class java/util/Objects, method requireNonNull, with exactly 1 argument, AND the stack is non-empty with stack.peek() being the identical Expression object as the argument (the dup twin — dup pushes the same reference, line 1932). In that case skip emitting the ExpressionStatement entirely. Alternatively implement as a small post-pass transform that drops ExpressionStatement(Objects.requireNonNull(x)) immediately preceding a statement whose method-ref receiver is x, but the in-decoder identity check is simpler and more precise.


### Suggested Approach

ClassFileToJavaSyntaxConverter pop handler case 0x57 (:1907-1919): before materializing a popped StaticMethodInvocationExpression as a statement, skip it when it is java/util/Objects.requireNonNull:(Ljava/lang/Object;)Ljava/lang/Object; with exactly one argument that is reference-identical to stack.peek() (the dup twin pushed at :1932) — the javac bound-method-ref null-check idiom. Guarding on identity + exact owner/descriptor preserves user-written requireNonNull calls. Cleans C_FunctionalInterfaces.useConsumer, C_Optional.ifPresentPrint, and the member-inner ctor preamble noise.

## Solution Implemented

Implemented exactly as the suggested approach: in the `case 0x57` pop handler of
`ClassFileToJavaSyntaxConverter`, before materializing a popped
`StaticMethodInvocationExpression` as an `ExpressionStatement`, the handler now skips it when it
is exactly `java/util/Objects.requireNonNull:(Ljava/lang/Object;)Ljava/lang/Object;` with one
argument that is REFERENCE-IDENTICAL to `stack.peek()` — the dup twin left by javac's bound
method-reference null-check idiom (`getstatic/aload receiver; dup; invokestatic
Objects.requireNonNull; pop; invokedynamic`). `dup` pushes the same `Expression` object, so the
identity check fires only for the compiler-synthesized pattern: user-written `requireNonNull`
calls (statement form, 2-arg form, result-used form) never leave their argument aliased on the
stack and are all preserved (verified).
