## Description

Class of defect: SILENT MISCOMPILATION (recompiles cleanly, computes wrong values). Matrix classes affected: C_FlexibleCtor, C_Records.

- **[CRITICAL] C_FlexibleCtor$Sub**: Ternary condition and else-branch silently dropped in the Sub(int, long) constructor. Original computes the absolute value of 'stamp' (bytecode confirmed: lcmp/ifge selecting between lneg and the raw value); decompiled output unconditionally negates the argument. For any positive stamp the recompiled code stores the wrong (negated) value into the final field 'stamp'. Recompiles cleanly, computes wrong values.
  - original: `long abs = stamp < 0 ? -stamp : stamp;
this.stamp = abs;`
  - decompiled: `long var4 = -arg1;
this.stamp = var4;`

## Technical Analysis

### C_Records (confidence: HIGH)

Bytecode is `new Slope; dup; iload_1; ifne; <NaN arm>; goto 51; <ddiv arm>; 51: invokespecial Slope.<init>(D)V; areturn` — new/dup precede the conditional, so the ternary's merge block (pc 51) consumes the per-arm value as a constructor argument. The per-block decoder handles this correctly: decodeBasicBlock seeds each block's operand stack from the predecessor's exitStack (ClassFileToJavaSyntaxConverter.java:1363-1376), and invokespecial <init> rebuilds `new Slope(NaN)` replacing the dup'd NewExpression (ClassFileToJavaSyntaxConverter.java:2288-2297), so the merge block decodes to a single statement `return new Slope(NaN)`. The defect is in StructuredFlowBuilder ternary Pattern 0: the BUG-2026-0025 shortcut at StructuredFlowBuilder.java:637-642 treats ANY merge block whose statements are exactly one ReturnStatement as a 'pure return' and emits `return <ternary>` at line 646, discarding the merge block's decoded ReturnStatement — it assumes the merge return returns the arm value directly, never checking whether the arm value is embedded deeper (here as a NewExpression constructor argument). The correct substitution path replaceTernaryInMergeStatements (StructuredFlowBuilder.java:647-652, impl 1629-1684) is short-circuited, and it only handles ExpressionStatement+MethodInvocationExpression anyway, not ReturnStatement or NewExpression. This refines the value-merge cluster: the per-arm values are intact; what is lost is the merge-block consumer expression wrapping them.

### Suggested Approach

StructuredFlowBuilder Pattern 0 (cfg/StructuredFlowBuilder.java:637-652): the BUG-2026-0025 shortcut treats any single-ReturnStatement merge block as a pure return and discards it, and replaceTernaryInMergeStatements (:1629-1684) only handles ExpressionStatement+MethodInvocationExpression. Fix: only emit 'return <ternary>' when the merge return expression identity-matches an arm value (reuse expressionMatchesValue :1686); otherwise generalize replaceArgWithTernary (:1647) into a recursive rewriter that substitutes the arm value inside ReturnStatement expressions, NewExpression/invocation arguments, VariableDeclarationStatement/AssignmentExpression RHS (the istore/lstore merge form behind C_FlexibleCtor's dropped abs() and BUG-2026-0053's dropped condition), CastExpression and BinaryOperatorExpression operands. Also stop folding 'int x = switch(...); return x+1;' into 'return switch' when post-switch computation exists (BUG-2026-0066 finding 5).

Per-finding fix details:

- In StructuredFlowBuilder.java Pattern 0 (lines 637-652): when mergeBlock has exactly one ReturnStatement with expression retExpr, only treat as pure return if retExpr matches trueValue or falseValue (identity match works — the merge stack is seeded with the same Expression objects from the predecessor's exitStack; reuse expressionMatchesValue at line 1686). Otherwise recursively substitute the subexpression of retExpr matching trueValue/falseValue with the ternary and emit `return <rewritten retExpr>`. Implement by generalizing replaceArgWithTernary (StructuredFlowBuilder.java:1647) into a recursive rewriter that also handles NewExpression arguments (plus MethodInvocationExpression receiver/args, BinaryOperatorExpression operands, CastExpression), and call it from a new ReturnStatement branch in replaceTernaryInMergeStatements. Result: `return new Slope(var1 == 0 ? Double.NaN : (double) var2 / (double) var1);`. Keep existing direct-return behavior (verified working via the `direct()` repro method) by falling back to `return ternary` when retExpr itself is the arm value.

## Solution Implemented

All changes in `StructuredFlowBuilder.java` (tags `BUG-2026-0083-20260610-1/2/3`). Root causes found
and fixed (the C_FlexibleCtor investigation showed the ternary DID form; the merge consumer
substitution and the post-merge continuation were broken):

1. **Pattern 0 pure-return shortcut narrowed** (tag -1). The BUG-2026-0025 shortcut treated ANY
   single-ReturnStatement merge block as a pure return and emitted `return <ternary>`, discarding
   the decoded return expression. It now takes the shortcut only when the returned expression IS
   the arm value (identity / constant match via `isTernaryArmValue`); embedded consumers like
   `return new Slope(cond ? a : b)` (C_Records) go through the generalized rewriter and keep the
   wrapping expression.

2. **Generalized recursive consumer rewriter** (tag -2). `replaceTernaryInMergeStatements` now:
   - Pass 1 (strict): finds the seeded arm-value reference by OBJECT IDENTITY anywhere in the
     merge statements (the merge block's operand stack is seeded with the same Expression objects
     as the branch `stackTopExpression`s — BUG-2026-0051 seeding) and substitutes the
     TernaryExpression in place, recursing through assignment LHS/RHS, declaration initializers
     (the C_FlexibleCtor `lstore`-to-declaration shape), invocation/constructor/static-call
     arguments and receivers, casts, unary/binary operands, array access, field access, nested
     ternaries, return and throw expressions, array dimensions.
   - Pass 2 (loose): retries the first statement with constant value-equality (re-decoded
     constants break identity).
   - Legacy fallbacks preserved bit-for-bit: lone-opaque-return -> `return ternary`
     (BUG-2026-0025), leading invocation -> force-replace last argument with receiver override
     (BUG-2026-0015), leading assignment -> force RHS. Last resort keeps the merge statements
     verbatim instead of dropping them.
   - Rendering safety: a ternary substituted as a DIRECT operand of a binary/unary expression
     would be emitted without the parentheses Java requires (`a + c ? x : y` re-parses as
     `(a + c) ? x : y`, sometimes still compiling with wrong semantics). The rewriter distributes
     the operation into the arms (`c ? a + x : a + y`) when evaluation-order-safe (other operand
     is a constant/local/`this`; condition side-effect-free for the right-operand case), and
     refuses the substitution otherwise (status-quo fallback) rather than emit a mis-parse.

3. **Post-merge continuation** (tags -1/-3). Direct consumption used to mark the merge block
   visited and truncate the method right after the ternary (`int a = c ? x : y;` followed by more
   code dropped EVERYTHING after the store — the BUG-2026-0069(c) "becomes constant" and
   BUG-2026-0053 "drops statements after the istore" shapes). Now:
   - merge block with statements: the substitution is done IN PLACE on the merge block's
     statement list, the block is NOT marked visited, and `lastEffectiveMergePoint` steers the
     caller INTO it so the regular machinery (conditional patterns, loops, return/goto/break
     handling) emits it exactly once and continues the flow.
   - merge block with NO statements that is itself a conditional (chained ternary arguments,
     e.g. `fmt(c1 ? a : b, c2 ? x : y)`: the merged value rides the operand stack): the ternary
     is registered in `pendingStackTernaries` and applied (strict identity) when the eventual
     consumer statement is rewritten; continuation proceeds into the merge block.
