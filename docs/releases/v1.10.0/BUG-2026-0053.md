# BUG-2026-0053: Ternary expression emitted as bare statement in lambda body

**Type**: Bug
**Status**: CLOSED (v1.10.0)
**Resolved**: 2026-06-10
**Severity**: HIGH
**Created**: 2026-04-21

## Description

Lambda bodies produced from synthetic BootstrapMethods include a ternary expression used as a bare statement, which is not valid Java:

```java
forEachInvocation(code, cp, (owner, name, desc, pc, it) -> {
    String scheme;
    "java.net.URL".equals(owner) == 0 || "<init>".equals(name) == 0
        ? "java.net.URI".equals(owner) != 0
            ? "<init>".equals(name) == 0 ? "create".equals(name) != 0 ? 1 : 0 : 1
            : 0
        : 1;      // <-- illegal: ternary used as statement
});
```

```java
minSev.addActionListener(() -> {
    AnalysisEngine.Severity threshold;
    String sel = (String) minSev.getSelectedItem();
    sel == null ? "All" : sel;   // <-- illegal: ternary used as statement
});
```

`error: not a statement`.

## Technical Analysis

The existing ternary-as-statement workaround (from v1.6.0, wraps orphan ternary in variable assignment) does not reach through synthetic lambda method bodies — the transformation likely runs on the outer method body only.

Occurrences observed:
- `it/denzosoft/springbootanalyzer/core/analysis/AnalysisEngine.java:1525`
- `it/denzosoft/springbootanalyzer/ui/panels/SecurityAnalysisPanel.java:129`

### Suggested Approach

Apply the ternary-as-statement transformation recursively into synthetic lambda bodies, or move the transformation to a single place in `JavaSourceWriter` that is invoked right before rendering any statement. Alternative: drop orphan ternary statements entirely — if the bytecode produced a value on the stack that was immediately popped, the equivalent source-level statement is a no-op.

### Affected Modules

- `src/main/java/it/denzosoft/javadecompiler/service/converter/ClassFileToJavaSyntaxConverter.java` (synthetic method body decode)
- `src/main/java/it/denzosoft/javadecompiler/service/writer/JavaSourceWriter.java` (lambda body emission)

### Estimated Effort

LOW

## Partial resolution via BUG-2026-0083 (2026-06-10)

The BUG-2026-0083 fix (StructuredFlowBuilder generalized ternary merge-consumer rewriter +
post-merge continuation) resolves the TERNARY aspects of this item, in lambda bodies included
(synthetic lambda methods go through the same per-method StructuredFlowBuilder path):

- No more bare ternary statement / ternary-as-expression-body for a void SAM: the ternary is now
  substituted into its real consumer (declaration initializer, store, argument, return value).
- No more dropped statements after the ternary's istore inside lambda bodies.
- The panel-style shape `String label = sel == null ? "All" : sel;` is no longer mis-decompiled
  as `String var2 = "All";` — condition preserved (verified: `T6Lambda`/`T6cLambdaTernary`
  round-trips; the collision-free variant compiles AND produces identical runtime output).

**What remains (item stays OPEN for this)**: lambda-body local variables are named from slot
numbers of the synthetic method and can collide with (shadow) enclosing-method locals — e.g.
`IntUnaryOperator var1 = ...; IntFunction var2 = p1 -> { String var1 = ...; }` fails to
recompile with "variable var1 is already defined". This is a NAMING defect in lambda body
emission, not a ternary defect; it needs a writer/converter-side rename of lambda-body locals
that clash with the enclosing scope (related to the inner-classes/captures cluster,
BUG-2026-0097).


## Solution Implemented (2026-06-10)

Fixed in three parts across the campaign:
1. **Ternary-as-bare-statement / consumer drop**: resolved by the BUG-2026-0083 generalized
   recursive consumer rewriter (ternary now lands in declaration/assignment/argument position
   inside lambda bodies; verified `p0 -> { String var3 = ...; String var4 = var3 == null ? "All" : var3; ... }`).
2. **Nested-ternary conditions kept raw (`x.equals(y) != 0` inside arms)**: BooleanSimplifier
   ternary branch now recurses into arms in VALUE context via new `simplifyTernaryValueArm`
   (conditions boolean-simplified, int-constant arm values preserved) — tags BUG-2026-0053-20260610-1/2
   in `service/converter/transform/BooleanSimplifier.java`.
3. **Leading `""` of a folded string concat dropped (`"" + i + j` emitted as int arithmetic)**:
   makeConcatWithConstants template path now forces string context on the leftmost LEAF of the
   `+` chain via `forceStringContextOnLeftLeaf` (root-level wrap would still sum ints first) —
   tags BUG-2026-0053-20260610-3/4 in `service/converter/ClassFileToJavaSyntaxConverter.java`.

### Files Modified
