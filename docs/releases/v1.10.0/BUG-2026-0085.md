# BUG-2026-0085: Statement-switch builder never emits break + cases built in key order not PC order

**Type**: Bug

**Created**: 2026-06-10
**Resolved**: 2026-06-10

## Description

Class of defect: SILENT MISCOMPILATION (recompiles cleanly, computes wrong values). Matrix classes affected: C_Java7StringSwitch, C_ControlFlow.

- **[HIGH] C_Java7StringSwitch**: All `break` statements dropped from the reconstructed string switch in category(String). Every case arm now falls through to the next, so the assignments cascade: "add"/"sub" assigns "arithmetic", falls into "and"/"or" which overwrites with "logical", falls into default which overwrites with "unknown". The method silently returns "unknown" for EVERY input. Verified at runtime: original yields add->arithmetic, and->logical, xyz->unknown; recompiled decompiled output yields unknown/unknown/unknown. The sibling method dayNumber() is unaffected only because its arms end in `return`. Root cause is in the assign-then-break switch pattern handling of the string-switch reconstruction (service/converter/transform/StringSwitchReconstructor path).
  - original: `switch (command) {
    case "add":
    case "sub":
        result = "arithmetic";
        break;
    case "and":
    case "or":
        result = "logical";
        break;
    default:
        result =`
  - decompiled: `switch (arg0) {
    case "add":
    case "sub":
        var1 = "arithmetic";
    case "and":
    case "or":
        var1 = "logical";
    default:
        var1 = "unknown";
}
return var1;`

## Technical Analysis

### C_ControlFlow (confidence: HIGH)

Three interacting defects in the statement-switch builder, StructuredFlowBuilder.java:312-426 plus findSwitchMergePoint:1383-1448. (1) findSwitchMergePoint's goto-count heuristic (1396-1416) finds no gotos because all cases physically fall through; the fallback (1420-1446) requires each case to reach the default via a goto and its walk hits 'isReturn -> break' (1434), so it returns -1 and caseStopPc becomes the method-level stopPc (-1) at line 332. (2) Case groups are built in switch-KEY order, not bytecode target-PC order (loop at 344-362), so key 1 — whose target 34 is the LAST link of the physical fall-through chain — is processed first and buildFromBlock (373) inlines the entire shared tail (iinc 100 default code + return) into case 1, marking blocks 34 and 37 visited. (3) Subsequent cases (key 2 -> 31, key 3 -> 28) are silently truncated when buildFromBlock0 hits the now-visited next block (line 152 'if (visited.contains(...)) return'), with no fall-through marker, duplication, or break; and the default case is skipped entirely because its target block 37 is already visited (guard at 381-383).

**Verifier correction**: Two trivial imprecisions, neither material: findSwitchMergePoint ends at line 1449 (return at 1448 is the last statement before the brace), and there is no separate 'return block' at PC 40 — leaders are only 0/28/31/34/37, so block 37 spans 37-41 and contains the ireturn (the fallback walk for case target 34 hits isReturn at block 37, one hop). Consequence for the fix: with next-target bounding, the default group bounded by method end correctly inlines 'var2 += 100; return var2;', so the proposed findSwitchMergePoint extension is optional for this method.

### C_ControlFlow (confidence: HIGH)

The statement-switch builder never emits BreakStatement. findSwitchMergePoint correctly returns 59 (two 'goto 59' counted at 1396-1404) and case bodies are built with caseStopPc=59 (StructuredFlowBuilder.java:332, 373). Inside buildFromBlock0, a case body ending with 'goto 59' takes the isGoto path (434): the labeled/plain break check at line 448 requires 'target.startPc > stopPc' (STRICTLY greater), which is false for target == merge == stopPc, so line 469 sets block = target and the loop returns at line 151 ('block.startPc == stopPc') without appending anything. The whileTrueExitStack break path (443-446) only covers while(true) exits. No code in the case-construction loop (363-377) or in JavaSourceWriter's SwitchStatement printing (JavaSourceWriter.java:1197) adds a break, so the printed cases have implicit fall-through that did not exist in the bytecode.

**Verifier correction**: One citation is wrong: JavaSourceWriter.java:1196-1197 is inside collectStatementImports (import collection), not SwitchStatement printing. The actual printer is the SwitchStatement arm of writeStatement at approximately lines 2325-2410, which emits sc.getStatements() verbatim and likewise synthesizes no break — so the substantive assertion ('no code in the writer adds a break') holds, only the line number is off.

### Suggested Approach

cfg/StructuredFlowBuilder.java SWITCH branch (:312-426) + findSwitchMergePoint (:1383-1449). Three fixes: (a) sort case groups by bytecode target PC ascending and slot the default at its PC position (fixes fall-through chain inlined into wrong case and dropped default in C_ControlFlow.switchWithFallAccumulate); (b) bound each case body with the NEXT group's target PC as stopPc so shared tails are never inlined and genuine fall-through is preserved; (c) emit BreakStatement when a case region's end block is a goto to switchMergePc (push merge PC on a switch-exit stack mirroring whileTrueExitStack :443-446) — this also restores the breaks StringSwitchReconstructor inherits, fixing C_Java7StringSwitch.category silently returning 'unknown' for every input.

Per-finding fix details:

- Rework case emission in StructuredFlowBuilder's SWITCH branch (lines 337-388): (a) after grouping keys by target, SORT the groups by target PC ascending and insert the default group at its PC position in that order (preserving bytecode layout, which is the original source case order); (b) bound each case body with the NEXT group's target PC as stopPc instead of the global caseStopPc, so a case that physically falls into the next case stops there and emits no break (genuine fall-through preserved) and shared tails are never inlined into a key-order-earlier case; (c) the default is then built at its own slot before any other case can consume block 37. With next-target bounding, findSwitchMergePoint returning -1 is harmless for body construction, but additionally extend it so that when gotoCounts is empty and all chains converge by fall-through, the merge is the first block after the last case region terminator (here 37 or the return block) so post-switch code (return var2) is emitted by the merge-continuation at 418-424.

- In StructuredFlowBuilder's case-building loop (after buildFromBlock at line 373) and for the default case (385), append 'new BreakStatement(block.lineNumber)' when the case region terminates by branching to switchMergePc and the last built statement is not a Return/Throw/Break/Continue: locate the case's end block (walk from targetPc up to caseStopPc, same idiom as findBlockEnd) and test 'endBlock.isGoto() && endBlock.branchTargetPc == switchMergePc' (also treat FALL_THROUGH whose endPc == switchMergePc on the LAST emitted case as break-or-nothing). Alternative equivalent implementation: push switchMergePc on a switch-exit stack (mirroring whileTrueExitStack, precedent at 443-446) and in buildFromBlock0's goto handling emit BreakStatement when target.startPc equals the active switch merge. The last case before the merge needs no break only if it is the final case; for correctness it is safe to always emit break when the goto-to-merge test holds.

## Solution Implemented

All three fixes from the suggested approach, in `StructuredFlowBuilder` (tags `BUG-2026-0085-20260610-1..14`):

1. **PC-ordered case groups with default slotted at its PC position** (tags -2, -3): after the
   BUG-2026-0017 key grouping, the default target is inserted as a group (null label list); when
   the default target equals a case group's target (tableswitch hole keys), that group BECOMES the
   default (labels subsumed — semantically identical). Groups are then insertion-sorted by target
   PC ascending, which is the original source case order. The legacy default-handling block now
   only runs when `switchKeys == null`.
2. **Next-target bounding** (tag -2): each case body is built with `stopPc` = the next group's
   target PC (last group: the switch merge). Shared fall-through tails are never inlined into a
   key-order-earlier case and genuine fall-through is preserved (no break emitted at a
   fall-through boundary).
3. **Break emission on verified goto-to-merge terminals only** (tags -1, -4, -5): a
   `switchMergeStack` mirrors `whileTrueExitStack`; in `buildFromBlock0`'s goto handling, a
   forward goto whose target equals the innermost enclosing switch's merge PC emits a plain
   `BreakStatement`. Additionally `appendSwitchBreak` appends a trailing break when the case
   region's physically last block is a goto-to-merge that the structured-pattern machinery
   swallowed (e.g. an `if` branching straight to the merge) AND the built body can still complete
   normally (`completesAbruptly` checks Return/Throw/Break/Continue, Block tails and
   IfElse-with-both-abrupt-arms — prevents unreachable-statement javac errors).
4. **Merge-detection hardening** (tags -7..-9, -10..-12, found while verifying on the
   decompiler's own classes): `findSwitchMergePoint` now (a) only accepts candidates at or after
   the highest arm entry PC (a loop back-edge inside an arm could win the goto vote and place the
   "merge" mid-arm); (b) keeps the default target as a candidate even when it is also a case
   target (tableswitch hole keys + empty source default); (c) ignores gotos originating at or
   beyond the current build bound (a nested switch used to adopt the OUTER switch's merge).
5. **Continuation bounding** (tags -6, -13): the post-pattern continuation never follows a merge
   into/past the innermost enclosing switch merge, and the switch's own merge continuation never
   walks past the current build bound (both only apply to forward bounds; a loop-header bound
   before the switch does not constrain).
6. **Selector correctness** (tag -14): `block.selectorExpression` (the exact expression popped by
   the tableswitch/lookupswitch opcode) now takes priority over the last-statement heuristic,
   which mistook an unrelated trailing assignment for the selector setup
   (`var2 = "1"; switch (arg1)` decompiled as `switch (var2.ordinal())`).
