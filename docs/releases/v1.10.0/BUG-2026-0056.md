# BUG-2026-0056: Try-catch-finally: catch body truncated and post-try code dropped

**Type**: Bug
**Status**: CLOSED (v1.10.0)
**Severity**: HIGH
**Created**: 2026-04-21
**Resolved**: 2026-06-10

## Description

When a method has:

- a try block with a `finally` implemented via BOTH the Java-compiler's pattern of *inlining* the finally on the normal path AND a synthetic any-catch handler;
- a catch block that composes an exception and throws it;
- additional statements *after* the try-catch-finally.

The decompiler truncates the catch body after the first assignment and drops every statement that follows the try block. The method ends without a return for a non-void signature.

Example from `SimogClient.consultaGara(String)` (contrp.be-springboot-22.2.66.jar):

Expected (reconstructed from bytecode):
```java
public ConsultaGaraResponse consultaGara(String cig) throws MyException {
    log.info("consultaGara - start: cig '{}', URL '{}'", cig, getWebServiceTemplate().getDefaultUri());
    String ticket = login(username, password);
    ...
    ConsultaGaraResponse resp = null;
    try {
        resp = (ConsultaGaraResponse) ((JAXBElement) getWebServiceTemplate()
            .marshalSendAndReceive(objectFactory.createConsultaGara(createConsultaGara))).getValue();
    } catch (Exception e) {
        String message = "consultaGara - ";
        if (e instanceof WebServiceTransportException && e.getMessage().contains("Unauthorized [401]")) {
            message = message + Utilities.MSG_ANAC_UTENZA_NON_AUTORIZZATA;
        } else {
            message = message + e.getMessage();
        }
        throw new MyException(message);
    } finally {
        logout(ticket);
    }
    log.info("consultaGara - end");
    return resp;
}
```

Current output (v1.8.0):
```java
public ConsultaGaraResponse consultaGara(String cig) throws MyException {
    String message;
    ...
    ConsultaGaraResponse resp = null;
    try {
        resp = (ConsultaGaraResponse) ((JAXBElement) ...).getValue();
    } catch (Exception e) {
        message = "consultaGara - ";          // <-- catch body stops here
    } finally {
        this.logout(ticket);
    }
    // <-- missing: log.info + return resp
}
```

## Technical Analysis

Bytecode layout:
- `try`  pc 77-103
- `finally (inlined on success path)` pc 103-108 → `logout(ticket); goto 187`
- `catch (Exception e)` pc 111-176 → compose message + `athrow new MyException(message)`
- `any-handler (finally)` pc 177-186 → `logout(ticket); athrow` (rethrow)
- `after try` pc 187-199 → `log.info("- end"); return resp`

Exception table:
```
77-103   Exception   -> 111
77-103   any         -> 177
111-179  any         -> 177
```

`TryCatchReconstructor` recognises the inlined-finally + any-handler pair and strips the inline `logout(ticket)` from the success path. Two things then go wrong:

1. **Catch body truncation**: Only the first assignment of the catch block is captured. The subsequent `instanceof` / message compose / throw statements are dropped. Most likely cause: the reconstructor stops walking catch-block statements at the first statement that is itself a try-internal pattern marker, or the `athrow` at the catch's terminator isn't registered as a statement before block tail processing.
2. **Post-try code dropped**: The code after pc 187 (the goto target of the success path) never makes it into the outer statement list. The reconstructor returns the try-catch-finally as the final statement of the method, losing the remaining basic blocks.

### Suggested Approach

- In `TryCatchReconstructor`, after materialising the try/catch/finally bodies, continue walking the block list from the first block whose `startPc >= endPc-of-any-handler` (or the success-path goto target) and append those blocks to the outer statement list.
- Audit the catch-body extraction to ensure all statements between `handlerPc` and the catch's natural exit (athrow / goto / return / next catch-start) are collected.

## Solution Implemented (2026-06-10)

### Root cause

`TryCatchReconstructor.collectHandlerStatements` walked handler basic blocks LINEARLY. On a
CONDITIONAL block it followed only the fall-through edge (the bytecode then-branch), so a catch
body containing `if (e instanceof X && e.getMessage().contains(...)) {...} else {...}` emitted
the then-branch unconditionally and silently dropped the condition and the else-branch. Several
adjacent defects in the same path compounded the symptom:

1. `removeDuplicatedFinally`'s Case-3 fallback removed the trailing N try-body statements by
   COUNT whenever they were plain expression statements — swallowing real statements like
   `sb.append("ok;")` after an if/else inside try+finally (Wave-3 S4 shape). The structural
   match it was supposed to back up could NEVER match assignments because
   `expressionSignature` fell back to the identity `Object.toString` for expression types
   without a value-based toString.
2. The decoder types a slot initialised from `aconst_null` as `Object`; `Object resp = null`
   assigned a `String` in the try and returned after the try did not recompile.
3. A variable declared inside the try body but referenced in a catch clause / after the try
   (`String r1 = t.consulta(...)` in try, `r1 = "EX:..."` in catch, used after) left dangling
   references; a variable whose slot was first stored by a catch's exception store never got a
   declaration at all (`promoteFirst` did not recurse into try statements).
4. A try region nested inside a structured statement (try-catch in a loop) or inside another
   handler (nested try in catch) found no top-level statements, so the whole group was dropped;
   in loops the increment block reached via the handler-skipping goto was also lost (emitted as
   a bare `continue` — infinite loop at runtime).
5. `InstanceOfPatternReconstructor.bindAmpersand` bound the instanceof OPERAND itself as a
   pattern variable (`e instanceof T e`, illegal Java) once the conditional was preserved.

### Fix

- `StructuredFlowBuilder.buildHandlerBody(...)` (new public entry): handler bodies that contain
  internal control flow (conditional/switch) are now structured by the full flow builder
  (if/else, short-circuit `&&`/`||`, switches, loops) instead of the linear walk;
  `TryCatchReconstructor` delegates via the new `setFlowBuilder(...)` hook
  (`handlerRegionHasControlFlow` dry-run decides, legacy walk otherwise).
- `removeDuplicatedFinally`: signatures are now computed recursively for all common expression
  node types, so the exact structural match (Case 1/2) actually works; the count-based Case-3
  fallback additionally requires a structural match with local variable names normalized
  ("$v"), so genuine inlined-finally copies that differ only by synthetic names still dedup but
  unrelated statements (different constants/targets) are never swallowed.
- `retypeNullObjectDeclarations`: `Object v = null` declarations are retyped when every
  assignment to `v` in the method has one single concrete reference type.
- Try-declared variables referenced in catch/finally/after-try are hoisted: declaration demoted
  to an assignment, a definite-assignment-safe declaration (null/zero initialised) prepended
  before the try. `promoteFirst` (converter) inserts a typed bare declaration BEFORE a try
  statement that contains the first assignment of an otherwise-undeclared variable.
- `applyGroup` factoring: exception-table groups can now be applied recursively inside compound
  statement bodies (try in loop/if/synchronized) and inside freshly decoded handler bodies
  (nested try in catch, via `pendingNestedGroups`); colliding nested catch variable names are
  disambiguated (`e` -> `e2`). The loop builder inlines an unvisited increment block at the end
  of the body when the trailing `continue` is the loop's only one (handler between body and
  increment).
- `renameVarInStatement/Expression` now recurse into structured statements
  (if/if-else/while/do-while/switch/synchronized/try) and instanceof/array-access expressions,
  and preserve node identity when nothing changed.
- `InstanceOfPatternReconstructor.bindAmpersand` never binds the operand itself.
