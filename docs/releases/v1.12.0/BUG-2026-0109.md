# BUG-2026-0109: statement-form pattern switches left as a raw typeSwitch dispatch

**Type**: Bug
**Status**: RELEASED
**Severity**: HIGH
**Created**: 2026-09-05
**Resolved**: 2026-09-06

## Description
A pattern switch whose arms do not merge into a single value was not reconstructed: the output kept
the raw `switch (SwitchBootstraps.typeSwitch(sel, idx))` dispatch with integer case indices, which
does not compile. 27 of the 31 JDK 25 `java.base` classes using `typeSwitch` were affected (87%) —
the largest remaining modern-Java gap after v1.11.0.

## Technical Analysis
The audit reported this as one defect, but measuring it against purposely isolated fixtures split it
into two with very different natures:

| Shape | Status before | Nature |
|---|---|---|
| expression form, type patterns | worked | — |
| expression form, record patterns (named and unnamed components) | worked | — |
| **statement form** (no value merge) | raw dispatch | **arm bodies are all present** |
| **multi-label arm** (`case Integer _, Long _`) | raw dispatch | arm VALUES missing |

That distinction is what made a fix possible. `StructuredFlowBuilder.tryBuildSwitchExpression` only
matches arms merging into a common return/store, so a statement switch falls through — but nothing is
actually lost in that case: each arm's body was emitted, only the dispatch was left in bootstrap form.
It can therefore be rebuilt by an AST pass.

The multi-label / guard-restart shape is genuinely different: its arm values are carried on the
operand stack to a merge the flow builder never rebuilds, so they are absent from the statement tree.
No post-hoc transform can recover them; that half remains open (see below).

## Solution Implemented
`SwitchStatement.SwitchCase` gained pattern labels (`patternTypes`, `patternBindings`, `nullLabel`),
mirroring what `SwitchExpression.SwitchCase` already had for the expression form, and the writer
renders them — including multi-pattern labels and `case null`. A pattern case reports
`isDefault() == false` despite carrying no expression labels, and suppresses the `.ordinal()`
coercion that an all-int-label switch would otherwise get.

The new `PatternSwitchStatementReconstructor` pass, wired into both flow paths, rewrites a raw
dispatch into a real pattern switch: it maps each case index to its bootstrap label, uses the
`typeSwitch` call's first argument as the selector, folds a leading `Type b = (Type) sel;` into the
pattern binding, maps index -1 to `case null`, and drops the now-dead `int idx = 0;` companion when
nothing else reads it.

**It rewrites only shapes it fully understands**, and this restraint is the important part. An arm
that assigns the dispatch index and loops back — the guard/restart scaffold of a multi-label or
guarded switch — is left untouched, as are constant labels (strings, numbers, enum constants). A
first version without that guard "reconstructed" those too: the output looked like valid Java while
still being an infinite `while (true)` with no return, AND the rewrite silenced the
`PATTERN_SWITCH_NOT_RECONSTRUCTED` diagnostic, turning a reported defect back into a silent one.

### Known residual — tracked as BUG-2026-0123
The 7 remaining bodies are the shapes this pass deliberately declines: constant-label switches
(`java/io/FilePermission`, the `java/text/*Format` family) and guarded / multi-label pattern switches.
Their arm values are missing from the statement tree, so reconstructing them requires the flow builder
to rebuild the stack-carried merge. All 7 are flagged by `PATTERN_SWITCH_NOT_RECONSTRUCTED`.
