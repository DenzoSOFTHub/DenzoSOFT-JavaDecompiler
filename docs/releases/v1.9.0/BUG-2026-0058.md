# BUG-2026-0058: invokedynamic dispatched on call-site name, not bootstrap factory

**Type**: Bug
**Status**: RESOLVED
**Severity**: CRITICAL
**Created**: 2026-06-08
**Resolved**: 2026-06-08

## Description
The `invokedynamic` decoder (`ClassFileToJavaSyntaxConverter.java` case `0xBA`) branches on the dynamic
call-site name from the NameAndType (`makeConcatWithConstants`, `typeSwitch`/`enumSwitch`) instead of the
bootstrap method's factory class. Every other bootstrap falls into a lambda fallback that fabricates
`arg0 -> { }`:
- `java/lang/runtime/ObjectMethods` (record `toString`/`hashCode`/`equals`) → `return arg0 -> { };`
  ("X is not a functional interface").
- bare `StringConcatFactory.makeConcat` (no recipe) → no branch.

## Technical Analysis
Root cause: dispatch keys on `methodName` (`ClassFileToJavaSyntaxConverter.java:2152-2166`); only
`makeConcatWithConstants` (2168) and `typeSwitch`/`enumSwitch` (2246) are handled; everything else reaches
the unconditional null-body lambda fallback (2365-2386). `ObjectMethods` appears nowhere in the source.

### Suggested Approach
Resolve the bootstrap factory first (`bsm.bootstrapMethodRef` → owner class + name) and branch on it:
`ObjectMethods` → emit a recognizable sentinel so the writer can suppress the implicit record member
(see BUG-2026-0059); `StringConcatFactory` → handle both `makeConcat` and `makeConcatWithConstants`;
`LambdaMetafactory`/`altMetafactory` → existing lambda/method-ref path; `SwitchBootstraps` → existing
pattern-switch path. Guard the null-body lambda fallback so it only fires for genuine LambdaMetafactory sites.

### Affected Modules
- `service/converter/ClassFileToJavaSyntaxConverter.java` (case 0xBA)

### Estimated Effort
MEDIUM

See `docs/reports/report-decompilation-defect-analysis.md` (defect F02) for full evidence.

## Solution Implemented
In the `0xBA` (invokedynamic) case of the bytecode decoder, the bootstrap **factory** class is now
resolved up front from `bsm.bootstrapMethodRef` (`pool.getMemberClassName(methodHandle[1])`) and used to
branch:
- `java/lang/runtime/ObjectMethods` → push a recognizable sentinel `StaticMethodInvocationExpression`
  (owner `java/lang/runtime/ObjectMethods`) instead of fabricating an `arg0 -> { }` lambda. The writer
  suppresses the surrounding implicit record member (BUG-2026-0059); if not suppressed, the sentinel still
  compiles unlike the old lambda garbage.
- bare `makeConcat` (no recipe) is now accepted alongside `makeConcatWithConstants`, gated on the
  `java/lang/invoke/StringConcatFactory` owner, and reconstructs as a `+` chain.

The synthetic bootstrap classes (`ObjectMethods`, `StringConcatFactory`, `SwitchBootstraps`) are also
excluded from the import block (they are decode sentinels, never real source references).

### Files Modified
- `service/converter/ClassFileToJavaSyntaxConverter.java` - factory resolution + ObjectMethods branch + bare makeConcat (case 0xBA)
- `service/writer/JavaSourceWriter.java` - `addImport` skips synthetic bootstrap classes
