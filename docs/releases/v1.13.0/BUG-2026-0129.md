# BUG-2026-0129: Inlined `finally` copies survive before nested exits (double execution)

**Type**: Bug
**Status**: RELEASED
**Severity**: CRITICAL
**Created**: 2026-09-07
**Resolved**: 2026-09-07

**Source**: `docs/reports/report-java25-and-beyond-analysis.md` section 2, Q1 (proposed as
BUG-2026-0129 there). Severity CRITICAL per the report; no lower rating exists elsewhere, so no
conflict to resolve.

## Description

javac inlines the `finally` body before **every** exit from the protected region. The decompiler
removes that inlined copy only when it sits at the **top level** of the try or catch body. A copy
placed before a `return`/`break`/`continue`/`throw` that is **nested** inside an `if`, loop, labelled
block or switch inside the try body survives into the output, so the action runs twice: once from the
surviving copy and once from the reconstructed `finally`.

For the `lock.unlock()` family this is not merely redundant — the second `unlock()` throws
`IllegalMonitorStateException`. The output compiles cleanly, so no gate catches it.

Reproducer (`java.base`, `java/util/concurrent/LinkedBlockingDeque.pollFirst(long,TimeUnit)`; the
`unlock` at pc 38-40 is OUTSIDE the protected ranges `[18,38)` and `[46,66)` — it is the inlined copy):

```java
try {
    E x;
    while ((x = this.unlinkFirst()) == null) {
        if (nanos <= 0L) {
            Object var8 = null;
            lock.unlock();          // inlined finally copy, kept
            return var8;
        }
        nanos = this.notEmpty.awaitNanos(nanos);
    }
} finally {
    lock.unlock();                  // runs again -> IllegalMonitorStateException
}
```

Scale (measured, JDK 25 `java.base`, 3,376 top-level classes, javac `-g`): **498 sites in 82 files**
(449 before `return`, 49 before `break`); 42 files are the `unlock()` family; **30 of the 82 files
recompile clean**, so the defect ships silently. Reproduces at `-g`, `-g:source,lines` and `-g:none`.

## Technical Analysis

`TryCatchReconstructor.removeDuplicatedFinally` (:1983-2041) has three cases:
1. the trailing N statements of the body list match the finally body;
2. the N statements immediately before a **top-level** `Return`/`Throw`;
3. a count-based tail of plain `ExpressionStatement`s that also matches structurally
   (tightened by BUG-2026-0056-8).

None of them descends into `IfStatement`/`IfElseStatement`/`WhileStatement`/`DoWhileStatement`/
`ForStatement`/`LabelStatement`/`SwitchStatement`/`BlockStatement` bodies, which is exactly where
javac puts the copy for a nested exit. `stripLeadingFinallyDuplicate` (:2046) only handles the
normal-completion copy that lands after the try.

### Suggested Approach

Make the dedup structural and recursive: walk every compound statement nested in the try body and in
each catch body; wherever the N statements immediately preceding a `Return`/`Throw`/`Break`/
`Continue` structurally match the finally body (reusing the existing `statementsMatchFinally` with
local-name normalisation), delete them. Only do this when a finally body was actually reconstructed
for the group. Do NOT extend the count-based Case 3 into nested bodies — that is the shape
BUG-2026-0056-8 had to tighten.

### Affected Modules

- `src/main/java/it/denzosoft/javadecompiler/service/converter/transform/TryCatchReconstructor.java`

### Estimated Effort

LOW-MEDIUM.

## Solution Implemented

`TryCatchReconstructor.removeDuplicatedFinally` now runs a recursive structural pass,
`stripFinallyCopiesBeforeExits`, over the try body and every catch body BEFORE the historical
Cases 1-3. The pass rebuilds each compound statement (`BlockStatement`, `IfStatement`,
`IfElseStatement`, `While`, `DoWhile`, `For`, `ForEach`, `Label`, `Synchronized`, `Switch` cases and
a nested `TryCatchStatement`'s try body and catch clauses) with its inner statement lists processed,
then deletes any run of N statements that structurally matches the finally body (the existing
`statementsMatchFinally`) and is IMMEDIATELY followed by an exit out of the protected region.

Deliberate restrictions:

- Only `Break`/`Continue` (at any level) and `Return` (nested only) count as exits. `Throw` is
  excluded: a throw inside the region is covered by the `any` handler, so javac emits no copy before
  it and a match there would always be a false positive.
- At the top level only `Break`/`Continue` are considered, so Cases 1-3 keep their historical
  `Return`/`Throw` behaviour unchanged.
- A nested try's own `finally` body is never touched - its statements are not copies of the outer
  finally.
- The count-based Case 3 was NOT extended into nested bodies (the shape BUG-2026-0056-8 tightened).
