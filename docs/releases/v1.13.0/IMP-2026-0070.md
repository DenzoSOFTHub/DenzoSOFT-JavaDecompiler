# IMP-2026-0070: DenzoDecompiler shared a stateful JavaSourceWriter

**Type**: Improvement
**Status**: RELEASED
**Severity**: HIGH (filed MEDIUM; raised on closure — the shared writer turned out to be one half of a
CRITICAL correctness defect, not just an API-contract wart)
**Created**: 2026-09-05
**Resolved**: 2026-09-07
**Resolved by**: [BUG-2026-0124](BUG-2026-0124.md) — the fix landed there; this item is the same defect
seen from the API side and is closed with it.

## Description
Filed by the Java 25+ audit: `DenzoDecompiler` held `private final JavaSourceWriter writer` while
`JavaSourceWriter` carries per-call mutable state (`currentResult`, `anonymousClassDisplayNames`,
`inlinedStaticFieldNames`, `capturedArgSubstitutions`, `unitTypeIndex`). One instance per thread was
therefore required, while CLAUDE.md documented the orchestrator as thread-safe. The audit rated it
MEDIUM on the reasoning that internal callers create one instance per class.

## Why the severity was raised on closure
That reasoning was too generous. Measuring a candidate fix for BUG-2026-0123 exposed the consequence:
`--batch` was **non-deterministic** — the same build over the same 3,376 `java.base` classes produced
211 differing files run to run, and the variants were not equivalent (a boolean-returning method came
out as `return false;` or as `return 0;`, which does not compile). The shared writer was one of the two
causes; the other was a static field in `BooleanSimplifier`. Both are recorded in BUG-2026-0124.

## Solution Implemented
`DenzoDecompiler.decompile()` now builds a fresh `JavaSourceWriter` per call, exactly as it already did
for the converter, so a single instance IS safe to share across threads. `BooleanSimplifier`'s
per-method flag moved to a `ThreadLocal` with save/restore.

### Files Modified
See BUG-2026-0124. Verified in the current tree on 2026-09-07:
- `DenzoDecompiler.java:130` constructs `new JavaSourceWriter()` inside `decompile()`; the former
  `private final` field is gone, replaced at :31 by a comment recording why it must stay that way.
- `DenzoDecompiler.java:111` does the same for `ClassFileToJavaSyntaxConverter`.

### Test Case
- Test class: `DecompilerTest`
- Test method: `testThreadSafetyDeterminism` (:921, wired at :97)
- Verifies: one shared instance driven by 8 threads over 400 classes produces output identical to the
  sequential reference. The pre-fix build diverged in 11-21 classes per run.

### Measured Result
| Gate | before | after |
|---|---|---|
| `java.base` batch, run-to-run differing files | 211 of 3,376 | **0** |
| Shared instance, 8 threads, 400 classes | 11-21 divergences | **0** |

## Note for future work
The documentation constraint this produced is now in CLAUDE.md under Code Constraints: per-method or
per-class state must never live in a static field; put it on the instance or in a `ThreadLocal` with
save/restore.
