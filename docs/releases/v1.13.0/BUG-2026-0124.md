# BUG-2026-0124: batch decompilation is non-deterministic, and one variant does not compile

**Type**: Bug
**Status**: CLOSED
**Severity**: CRITICAL
**Created**: 2026-09-07
**Resolved**: 2026-09-07

## Description
Running `--batch` twice over the same input with the same build produces different output.
Measured on JDK 25 `java.base` (3,376 top-level classes): **211 files differ, 1,194 lines**, run to run.

The differences are not cosmetic. A boolean-returning method comes out as either

```java
return false;    // correct
return 0;        // does not compile
```

so a given class may decompile correctly in one run and produce uncompilable output in the next.
This affects `--batch`, which is the mode used on real jars.

## Evidence
```
rm -rf det1 det2 && mkdir det1 det2
java -cp target/classes it.denzosoft.javadecompiler.Main --batch <java.base> det1
java -cp target/classes it.denzosoft.javadecompiler.Main --batch <java.base> det2
diff -rq det1 det2 | wc -l      # 211
```
First differing file: `com/sun/crypto/provider/PBES1Core.java` line 61, `return 0;` vs `return false;`.

**Single-class decompilation is deterministic**: the same class decompiled six times through
`--compact` produced six byte-identical outputs, all with the correct `return false;`. Only the
batch path varies, which points at the thread pool.

Diagnostic-marker counts are stable across runs (`SwitchBootstraps.typeSwitch` 5, `__MONITORENTER__`
0, `/* inline stmt */` 0, `STACK_UNDERFLOW` 7), so metrics built on marker counts remain reliable;
the variance is in the boolean-coercion dimension.

## Technical Analysis
The affected rendering is the coercion of a leaked int-constant arm value to a boolean literal when
the merge's consumer is boolean-typed (introduced by BUG-2026-0066). Getting `0` instead of `false`
means the consumer's type was not known at that moment.

`BatchDecompiler` creates a `DenzoDecompiler` per class task and shares only the `Loader`, and no
static mutable field was found in `src/main/java`. Candidates not yet excluded:
- inner-class decompilation re-entering the converter through the shared loader;
- a per-instance cache on the shared `Loader` or `ClassPool`;
- ordering effects where a class's decompilation consults data populated by a previously decompiled
  class (which in batch depends on thread interleaving).

Note this also means **A/B comparisons of batch output across builds carry ~200 files of noise**;
compare marker counts, or decompile single classes, when attributing a change.

### Confirmed trigger: the thread pool
Driving `BatchDecompiler` directly with **threadCount = 1** over the same 3,376 classes produces
byte-identical output across two runs (0 differing files), while the default multi-threaded batch
differs in 211. Concurrency is therefore the trigger, not input ordering or a time budget.

Single-threaded output is also the CORRECT one: `PBES1Core` renders `return false;` at one thread and
`return 0;` in one of the two multi-threaded runs. Counting files containing a `return 0;` over the
same corpus gives **170 single-threaded against 256 multi-threaded** — roughly 86 classes where
concurrency alone turned a boolean return into an int.

### Root cause
`BooleanSimplifier.methodReturnIsBoolean` was a plain **static mutable field**. The entry point wrote
it, ran the simplification, and reset it:

```java
methodReturnIsBoolean = returnIsBoolean;
List<Statement> result = simplifyBooleanComparisons(statements);
methodReturnIsBoolean = false;
```

It is per-METHOD state held in per-PROCESS storage. Under the batch thread pool, one thread's write or
reset lands while another is mid-simplification, so a boolean-returning method sees `false` and its
`return 0` is never converted to `return false` — output that does not compile.

An earlier sweep for static mutable fields missed it because the grep also matched static nested
class declarations and the real hit was buried; a precise pattern found exactly one field in the whole
of `src/main/java`, and it was this one.

## Solution Implemented
The flag moved to a `ThreadLocal`, with save/restore around the call rather than a reset to a
constant, so a nested `simplify()` cannot clobber an enclosing method's flag either.

Separately, `DenzoDecompiler` held one shared `JavaSourceWriter` across all `decompile()` calls, and
that writer carries per-class state (configuration flags, inlined static-field names, anonymous-class
display names, the compilation-unit type index). A writer is now created per call, exactly as the
converter already was. **A single `DenzoDecompiler` instance is now safe to use from several
threads**, which the previous documentation explicitly warned against.

### Files Modified
- `src/main/java/it/denzosoft/javadecompiler/service/converter/transform/BooleanSimplifier.java` —
  static flag replaced by a `ThreadLocal` with save/restore
- `src/main/java/it/denzosoft/javadecompiler/DenzoDecompiler.java` — per-call `JavaSourceWriter`

### Test Case
- Test class: `DecompilerTest`
- Test method: `testThreadSafetyDeterminism`
- Verifies: four classes mixing boolean and int returns, decompiled sequentially and then 160 times
  across 8 threads through ONE SHARED `DenzoDecompiler`, produce identical output. On the pre-fix
  build it fails, and fails differently each run (2 classes, then 1).
