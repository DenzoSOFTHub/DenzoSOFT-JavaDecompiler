# BUG-2026-0122: statements displaced out of the try region

**Type**: Bug
**Status**: PARTIALLY RESOLVED
**Severity**: HIGH
**Created**: 2026-09-05
**Resolved**: 2026-09-07 (classes without line information; the line-bearing case stays open)

## Description
A statement whose bytecode lies inside a protected range could be emitted AFTER the catch clause.
Reproducer (`-g:none`):

```java
int f(String s) {
    int r = 0;
    try { Object o = null; r = o == null ? 1 : 2; }
    catch (RuntimeException e) { r = -1; }
    return r;
}
```
decompiled to
```java
int var2 = 0;
Object var3 = null;
try { var3 = null; } catch (RuntimeException e) { var2 = -1; }
var2 = var3 == null ? 1 : 2;      // bytecode is inside [2,16); emitted outside
```

## Technical Analysis
BUG-2026-0100 gave statements a bytecode position and classified regions on it, but only when the
region had NO line information. That was expected to fix this too. It did not, and measuring showed
why: the displaced statement is one the FLOW BUILDER synthesised — a merged ternary — so it is a new
object that never passed through the decoder. It carries **`pc = -1` and `line = 0`** (verified with a
temporary trace), so neither criterion could place it and it fell through to the "after" bucket.

A second effect was found in the same investigation: a group can hold SEVERAL protected ranges
sharing one handler. `sun/security/ec/SunEC$ProviderService.newInstance` has three — [46,71),
[72,88), [89,105) — all targeting handler 817, and membership was tested against the first entry only.

## Solution Implemented
- Statement ORDER is preserved from the decode, so an unpositioned statement (`pc < 0`, `line <= 0`)
  now inherits the classification of its predecessor rather than defaulting past the handler. A
  positioned statement beyond the group's end sets a latch so a later unpositioned one is not pulled
  back in.
- Region membership is tested against the UNION of the group's ranges, not just the first entry.
- `ModernTwrReconstructor` now recognises javac's suppression wrapper
  (`try { r.close(); } catch (Throwable t2) {}`) both in `isCloseAndRethrow` and in `closeVarsOf`;
  without it a try-with-resources stops collapsing as soon as the resource declaration is placed
  before the try, which is where its bytecode says it belongs.

## Still open: classes WITH line information
Enabling the bytecode criterion for line-bearing classes as well fixes the displacement there too and
was tried. It is **not shipped**, and the reason is worth recording.

On `java.base` it changes the emitted `catch (` count by **756**. Part of that is removing genuine
FABRICATIONS: `sun/security/ec/SunEC$ProviderService` has exactly ONE exception region in its bytecode
(verified with `javap`), yet the line-based grouping emits **19** catch clauses, 18 of them wrapping
code that has no handler at all, with empty bodies. Deleting those is right.

But at least one REAL handler disappears with them — that same class ends up with 0 — and losing a
handler is the gravest defect class in this project. Extending the group-union fix above was not
enough to recover it. Until the fabrications and the losses can be separated and measured apart, the
criterion stays restricted to regions without line information.

Anyone resuming this: the two populations are distinguishable. Count real exception regions per class
with `javap -p -c` and compare against the emitted `catch (` count, per class, before and after. That
turns "756 fewer" into "N fabrications removed, M handlers lost", which is the number that decides it.
