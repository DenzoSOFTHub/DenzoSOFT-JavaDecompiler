## Description

Without a LineNumberTable the region has no start line, so the line-span test rejected EVERY compound body and a try nested in a loop or an if lost its catch clauses at -g:none. applyGroup decides region membership by bytecode pc in that mode and returns null when the body holds no statement of the region, so every body can simply be offered.

## Technical Analysis

Transcribed from the change comments, in progressive order:

- **BUG-2026-0137-1** (`src/main/java/it/denzosoft/javadecompiler/service/converter/transform/TryCatchReconstructor.java:1006`): Without a LineNumberTable the region has no start line, so the line-span test rejected EVERY compound body and a try nested in a loop or an if lost its catch clauses at -g:none. applyGroup decides region membership by bytecode pc in that mode and returns null when the body holds no statement of the region, so every body can simply be offered.
- **BUG-2026-0137-2** (`src/main/java/it/denzosoft/javadecompiler/service/converter/transform/TryCatchReconstructor.java:274`): One source `try` can own SEVERAL protected ranges: javac splits the range around code it excludes (e.g. the `areturn` of a `return` inside the try: [26,46)->56 and [47,56)->56). Grouping by (startPc, endPc) made each fragment its own try, so the body was wrapped twice in nested try/catch with the same clause and the code of the second fragment (`throw new ISE(s)`) ended up OUTSIDE both - an exception the source caught escaped the method. A handler pc belongs to exactly one source try statement, so regions whose (handlerPc, catchType) sets are identical are fragments of the same try: merge them into one group keyed by the union range.
- **BUG-2026-0137-3** (`src/main/java/it/denzosoft/javadecompiler/service/converter/transform/TryCatchReconstructor.java:329`): Merge range fragments of one source try.
- **BUG-2026-0137-4** (`src/main/java/it/denzosoft/javadecompiler/service/converter/transform/TryCatchReconstructor.java:421`): A merged group spans all its fragments.
- **BUG-2026-0137-5** (`src/main/java/it/denzosoft/javadecompiler/service/converter/transform/TryCatchReconstructor.java:519`): The gap between two fragments of one source try is code javac excluded from the protected range (the `areturn` of a `return` inside the try, an inlined finally copy) - still try-body code. `if (s.equals(n)) return s.toUpperCase();` (position = its areturn pc, in the gap) was otherwise moved after the catch.
- **BUG-2026-0137-6** (`src/main/java/it/denzosoft/javadecompiler/service/converter/transform/TryCatchReconstructor.java:560`): A statement of a block that starts between two LineNumberTable entries carries no line (0): the code after `if (c) return x;` written on the same source line. The line test cannot place it, and it was pushed out of the try (`throw new ISE(s)` escaped its catch). Its bytecode position can: a recorded pc inside the group's protected span is try-body code.
- **BUG-2026-0137-8** (`src/main/java/it/denzosoft/javadecompiler/service/converter/ClassFileToJavaSyntaxConverter.java:5803`): A body holding ONLY the synthetic try { lock; ENTER; ...; EXIT } finally { EXIT } (a synchronized block that is the sole statement of an if branch whose region the try reconstructor now finds) must be unwrapped too; the size<2 shortcut skipped stripMonitorFromTryFinally and left the try/finally with a raw __MONITOREXIT__ marker around the rebuilt synchronized.
