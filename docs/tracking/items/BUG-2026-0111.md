# BUG-2026-0111: try-with-resources combinations not reconstructed

**Type**: Bug
**Status**: IN_ANALYSIS
**Severity**: HIGH
**Created**: 2026-09-05
**Source**: `docs/reports/report-java25-plus-audit.md` §BUG-2026-0111 (audit of 2026-09-05, v1.10.0
baseline). Confirms/refines the ROADMAP entry "Multi-resource effectively-final TWR" and BUG-2026-0068.

## Description
Three try-with-resources shapes fail to collapse, each producing code that does not compile or that
misplaces declarations:
1. **Multi-resource effectively-final** (`try (r1; r2)`): a variable is used before it is declared, the nested try emits a bare `throw e`, and a stray `Reader var3 = r2;` appears after the try.
2. **TWR + catch + finally**: the resource is left undeclared and assigned a wrong value (`buf = "io"`).
3. **TWR body locals** leak or vanish.

Evidence (audit workspace): `probe/dec/P_Structured.java:30-56` (shape 1), `:58-80` (shape 2),
`probe/dec/P_ModernApis.java:24-40` (`if (ex == null) {...; return;} throw f;`).

## Technical Analysis
- `transform/ModernTwrReconstructor` matches typed resources in ONE shape only: `R r = init; try {body} catch (Throwable t) { r.close(); throw t; } r.close();`
- LVT flattening (BUG-2026-0103, released v1.11.0) renamed the `Throwable` slot, which the matcher depends on.
- `TryCatchReconstructor.isHandlerProtectionEntry` coalesces only identical `(handlerPc, catchType)` pairs, so an enclosing user `catch`/`finally` is not re-attached to the same `TryCatchStatement`.

**Re-verified 2026-09-07**: `isCloseAndRethrow` (:196) and `closeVarsOf` (:221) are still the single
recognised shape in `ModernTwrReconstructor.java`. Note that BUG-2026-0125 (v1.13.0) has since taught
both of them javac's suppression wrapper — that change is adjacent to this item and any work here
must not undo it.

### Note on severity
The audit rated this HIGH, the original index row MEDIUM. Resolved to **HIGH** per the project rule:
where two sources disagree on severity, the more critical one stands. Under-rating a defect costs more
than over-rating it, because it is what decides whether the item is looked at at all.

### Suggested Approach
Do this AFTER BUG-2026-0103 (done, v1.11.0):
- Accept the effectively-final alias form (`Object v = r; ... if (v != null) v.close();`).
- Recognise the nested resource ladder recursively, innermost outward.
- Re-attach the enclosing user `catch`/`finally` group as clauses of the same `TryCatchStatement`.
