# BUG-2026-0126: statements displaced out of the try region in classes WITH line information

**Type**: Bug
**Status**: IN_ANALYSIS
**Severity**: HIGH
**Created**: 2026-09-07
**Parent/related**: split from BUG-2026-0122 — the half that remains open; the fixed half is
BUG-2026-0125.

## Description
`TryCatchReconstructor` classifies statements into/out of a protected region by SOURCE LINE whenever
the region has line information, and only falls back to the exact bytecode-pc criterion when it does
not. So with a LineNumberTable a statement whose bytecode lies inside the range can still be emitted
after the catch clause, and vice versa.

Reproducer: `S_Sync.slotReuse` emits `r = f == null ? 1 : 2;` AFTER the catch clause although its
bytecode lies inside the exception range `[2,16)`.

The wider consequence is what makes this more than cosmetic: **output depends on source formatting**.
Two classes with identical bytecode but different line tables decompile differently. This affects every
jar built by Maven or Gradle, since those emit full debug information.

## Technical Analysis
`TryCatchReconstructor.applyGroup` is where the classification happens; the pc map and `minPcOf` it
needs already exist (added by BUG-2026-0100).

### What was already tried, and why it is NOT shipped
Enabling the bytecode criterion for line-bearing classes as well fixes the displacement, and was
tried. On `java.base` it changes the emitted `catch (` count by **756**.

Part of that is removing genuine FABRICATIONS: `sun/security/ec/SunEC$ProviderService` has exactly ONE
exception region in its bytecode (verified with `javap`), yet the line-based grouping emits **19**
catch clauses, 18 of them wrapping code that has no handler at all, with empty bodies. Deleting those
is right.

But at least one REAL handler disappears with them — that same class ends up with 0 — and losing a
handler is the gravest defect class in this project. Extending the group-union fix from BUG-2026-0125
was not enough to recover it. Until the fabrications and the losses can be separated and measured
apart, the criterion stays restricted to regions without line information.

### Suggested Approach
The two populations are distinguishable, and separating them is the prerequisite, not the fix itself.
Count real exception regions per class with `javap -p -c` and compare against the emitted `catch (`
count, per class, before and after. That turns "756 fewer" into "N fabrications removed, M handlers
lost", which is the number that decides whether the criterion can be switched.

`ModernTwrReconstructor` is tuned against the line-based shape and is what regresses first (the `TwrT`
test catches it), so it has to move in step with any change here.
