# BUG-2026-0132: `break`/`continue` out of a `synchronized` block inside a loop deletes the block body

**Type**: Bug
**Status**: TO_ANALYZE
**Severity**: CRITICAL
**Created**: 2026-09-07

**Source**: `docs/reports/report-java25-and-beyond-analysis.md` section 2, Q4. Generalises
BUG-2026-0121 (index: HIGH) and explains the 12 residual `__MONITOREXIT__` files. Report says
CRITICAL, BUG-2026-0121 says HIGH -> the more critical reading wins: **CRITICAL**.

## Description

When a `synchronized` block inside a loop is left by `break`/`continue`, javac emits an exit-path
`monitorexit` followed by the jump. The reconstructor treats that first depth-matched exit marker as
the END of the monitor region, so everything the flow builder placed between it and the real region
end is dropped by the surrounding try/finally reconstruction. The body of the `synchronized` block
disappears; what is left often still compiles.

`java/util/concurrent/Phaser.doRegister` (javap pc 185-284) decompiles to

```java
synchronized (this) {
    if (this.state != s) {
        try { /* __MONITOREXIT__ */ } finally { /* __MONITOREXIT__ */ }
    }
}
```

— the condition is inverted and `parent.doRegister(1)`, the `break`s, `next = ...` and the CAS loop
are gone. `java/util/TimerThread.mainLoop` loses `queue.removeMin(); continue;`,
`if (!taskFired) queue.wait(...)` and `if (taskFired) task.run()`, and gains a fabricated
`try { ... } catch (InterruptedException e) {}`.

Probe `SCRATCH/probe/src/P_SyncBreak.java` reproduces it in **all three debug modes** (`f(1)`,
`cas(...)`, `remove(0)`, `wait(10L)`, `f(2)` all absent from the output).

## Technical Analysis

`ClassFileToJavaSyntaxConverter.reconstructSynchronized` (:5272-5430) pairs
`__MONITORENTER__`/`__MONITOREXIT__` markers as balanced parentheses in statement order;
`collectSynchronizedRegion` (:5430-5480) terminates the region at the first depth-matched exit
marker. The break-path exit marker comes first, so the region closes there. The `any` handler that
covers the region is then turned into `try { } finally { /* __MONITOREXIT__ */ }` and its body is
discarded.

BUG-2026-0121 established that the if/else inversion comes from `StructuredFlowBuilder`, not from the
reconstructor, and that a reconstructor-only fix dropped the handler. Do not repeat that.

### Suggested Approach

Model exit-path monitorexits explicitly: an `__MONITOREXIT__` immediately followed by a
`break`/`continue`/`return`/`throw` (or by a `goto` leaving the monitor's `any` range) is an *exit
copy*, not the region end. Mark those and have `collectSynchronizedRegion` skip them; the region ends
at the exit marker whose successor is the fall-through merge. Pair with a block-coverage check so any
residual loss is reported instead of silent.

### Affected Modules

- `service/converter/ClassFileToJavaSyntaxConverter.java` (decoder + `reconstructSynchronized` +
  `collectSynchronizedRegion`)
- possibly `StructuredFlowBuilder.java`

### Estimated Effort

MEDIUM-HIGH.

## Update 2026-10-30 (v1.13.0 release build)

The runtime-oracle fixture `src/test/resources/runtime-oracle/RSyncLoopExit.java` changed failure
class between commit `e032be5` and the v1.13.0 release build:

| Build | `-g` / `-g:source,lines` / `-g:none` |
|---|---|
| `e032be5` | exit 2 — does not recompile (`missing return statement`) |
| v1.13.0 release | exit 3 in all three modes — **recompiles, behaves differently** |

The computed values now match; the difference is that the statements following the
`synchronized` block inside the loop are emitted inside it, so they run with the monitor held
(`log= bt=true ct=true ...` instead of `bt=false ct=false ...`). `continueThenTail` also carries a
`/* __MONITOREXIT__ */` marker. This is the silent class: the defect is no longer visible to a
recompile gate, which makes this item more urgent, not less.
