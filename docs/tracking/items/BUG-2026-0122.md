# BUG-2026-0122: Statements displaced out of the try region when line numbers are present

**Type**: Bug
**Status**: TO_ANALYZE
**Severity**: HIGH
**Created**: 2026-09-05

## Description
With a LineNumberTable, statements whose source line falls outside the region's line span are placed outside the `try` even though their bytecode lies inside it — and vice versa. Example: `S_Sync.slotReuse` emits `r = f == null ? 1 : 2;` (bytecode inside the exception range [2,16)) AFTER the catch clause. Also makes results depend on source formatting: two classes with identical bytecode but different line tables decompile differently.

## Technical Analysis
`TryCatchReconstructor.applyGroup` classifies by source line. BUG-2026-0100 introduced an exact bytecode-pc criterion and the statement/pc map that feeds it, but applies it only when the region has NO line information, because switching wholesale changed grouping for line-bearing classes and regressed try-with-resources collapse (`ModernTwrReconstructor` is tuned against the line-based shape; caught by the `TwrT` test).

### Suggested Approach
Extend the pc criterion to line-bearing classes and adapt `ModernTwrReconstructor` (and any other shape-matching transform) to the corrected grouping. Gate with the full three-mode matrix plus the TWR tests; the pc map and `minPcOf` already exist.
