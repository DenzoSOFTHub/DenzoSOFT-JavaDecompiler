# BUG-2026-0109: statement-form pattern switches fall back to a raw typeSwitch, losing arm values

**Type**: Bug
**Status**: IN_PROGRESS
**Severity**: HIGH
**Created**: 2026-09-05

## Description
A pattern switch whose arms do not merge into a single return/store is not reconstructed: the output
keeps the raw `switch (SwitchBootstraps.typeSwitch(sel, idx))` dispatch with integer case indices,
**and the arm values are missing entirely**. A `return switch (...)` method can end up with no
`return` at all, wrapped in `while (true)`.

27 of the 31 JDK 25 `java.base` classes that use `typeSwitch` are affected (87%).

```java
// source
static String pat(Object o) {
    return switch (o) {
        case Point(int x, _) -> "x=" + x;
        case Box(_)          -> "box";
        case String _        -> "str";
        default              -> "?";
    };
}
// decompiled: every arm value is gone, no return
while (true) {
    switch (SwitchBootstraps.typeSwitch(var1, var2)) {
        case 0: Point var3 = (Point) var1; int x = var3.x(); ... break; break;
        case 1: Box var5a = (Box) var1; Object var6a = var5a.v(); break;
        case 2: break;
        default: break;
    }
}
```

## Technical Analysis
`StructuredFlowBuilder.tryBuildSwitchExpression` matches only arms that merge into a common
return/store. It does not match:
- statement-form switches whose arms `break` to a merge point;
- record patterns with unnamed components, whose dead temporaries (`int var6 = var5;`) break the
  expected arm shape;
- multi-label type arms (`case 0: case 1:` sharing one instanceof chain).

The arm VALUES are carried on the operand stack to that merge, so when the merge is not rebuilt they
are not merely mislabeled — they are absent from the statement tree. Recovering them is flow-builder
work on stack-carried merges, not a post-hoc AST rewrite: no transform over the emitted statements can
invent values that were never emitted.

### Suggested Approach
Extend the flow builder to recognise the `while (true) { switch (typeSwitch(sel, idx)) { ... } }`
scaffold and rebuild the merge: map each case index to its label (already available via
`patternSwitchLabels`), fold `Type b = (Type) sel;` heads, treat `idx = N; continue` as a failed
guard (`when`), merge `case i: case j:` bodies into `case A _, B _`, and take each arm's value from
the stack snapshot at its exit block.

### Affected Modules
- `service/converter/cfg/StructuredFlowBuilder.java`
- possibly a new `service/converter/transform/PatternSwitchStatementReconstructor.java`

## Partial work done in v1.12.0
The reconstruction itself is NOT implemented. What was delivered is the honesty half, because this
output was **silently** wrong: only 3 of the 29 affected `java.base` files carried any diagnostic, so
a reader had no signal that arm values were missing.

`containsRawTypeSwitch` now detects a surviving raw dispatch in the emitted body (both the legacy and
the JD path) and records:

```
PATTERN_SWITCH_NOT_RECONSTRUCTED -- raw SwitchBootstraps.typeSwitch dispatch emitted;
arm values were carried on the operand stack and are missing from this body
```

Coverage 27 of 28 real cases. The miss is `java/lang/Module`, where the switch sits inside an inline
lambda body: the detector walks statements, and a lambda reaches the tree as an expression (a method
argument), so descending would need an expression walker. (`java/lang/runtime/SwitchBootstraps`
itself matches a plain grep for the name but contains no raw dispatch.)
