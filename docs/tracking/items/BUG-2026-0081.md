# BUG-2026-0081: invokespecial super.m() emitted as this.m() — infinite recursion

**Type**: Bug
**Status**: RESOLVED
**Severity**: CRITICAL
**Created**: 2026-06-10
**Resolved**: 2026-06-10
**Cluster**: `super-call-virtualized` (construct-matrix gap analysis, fix order #1)
**Parent/related**: NEW — umbrella BUG-2026-0080

## Description

Class of defect: SILENT MISCOMPILATION (recompiles cleanly, computes wrong values). Matrix classes affected: C_Circle.

- **[CRITICAL] C_Circle**: Super call silently converted to virtual self-call, producing infinite recursion. Bytecode is 'invokespecial C_Shape.describe' (a super.describe() call), but the decompiler emitted 'this.describe()', which dispatches virtually back to C_Circle.describe(). The recompiled method recurses forever and throws StackOverflowError instead of returning "Circle: " + the superclass description. Compiles cleanly, computes nothing.
  - original: `String describe() {
    return "Circle: " + super.describe();
}`
  - decompiled: `String describe() {
    return "Circle: " + this.describe();
}`

## Technical Analysis

Root cause documented in the verified semantic-divergence audit (see report-construct-matrix-gap-analysis.md). The mechanism lives in the modules listed below.

### Suggested Approach

In service/converter/ClassFileToJavaSyntaxConverter.java case 0xB6/0xB7/0xB9 (:2242-2335), the non-<init> branch builds a plain MethodInvocationExpression with a ThisExpression receiver, losing the invokespecial (non-virtual) semantics. Fix: when opcode==0xB7, methodName!=<init>, receiver is ThisExpression, and the target class is not currentClassInternalName (i.e. a superclass method; keep this.m() for same-class private methods), set a new superCall flag on MethodInvocationExpression; in service/writer/JavaSourceWriter.java's invocation branch print 'super.' instead of 'this.' when the flag is set. Add a round-trip test calling super.describe() from an override.

## Solution Implemented

In `ClassFileToJavaSyntaxConverter` case 0xB6/0xB7/0xB9, the non-`<init>` branch now checks:
`opcode == 0xB7` (invokespecial) AND receiver is `ThisExpression` AND the constant-pool target
class differs from `currentClassInternalName` AND the cp entry tag is `CONSTANT_Methodref`
(not `CONSTANT_InterfaceMethodref`). When all hold, the invocation is a super-call and the
receiver is replaced with a marker that renders as the bare keyword `super`.

**Deviation from the suggested approach**: the suggested `superCall` flag on
`MethodInvocationExpression` plus a `JavaSourceWriter` branch was NOT used, because both files
were owned by other concurrent work streams and the writer has no existing super-receiver
representation (only the `methodName=="super"` ctor-call branch, which renders `super(args)`).
Instead, a converter-only marker (`buildSuperReceiver`) composes two existing, stable writer
behaviours: a prefix `UnaryOperatorExpression` prints its operator string verbatim, and an
instance `MethodInvocationExpression` named `access$...` prints nothing (synthetic-accessor
suppression). The composition renders exactly `super`, so the call emits `super.m(args)`.
A first-class `SuperExpression`/flag can replace the marker later without behavior change.

Scope notes:
- Same-class invokespecial (private methods, `this.m()`) keeps the `this.` receiver — verified.
- `Interface.super.m()` default-method calls (InterfaceMethodref) are deliberately excluded and
  keep the previous `this.m()` form (separate pre-existing limitation; plain `super.` would
  resolve to the wrong type). Verified not to regress (EdgeSub round-trip runtime-identical).
- Constructor `super(...)`/`this(...)` paths are untouched.
