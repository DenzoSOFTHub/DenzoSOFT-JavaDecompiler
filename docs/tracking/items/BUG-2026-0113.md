# BUG-2026-0113: erased casts rendered instead of the generic target

**Type**: Bug
**Status**: IN_ANALYSIS
**Severity**: MEDIUM
**Created**: 2026-09-05
**Source**: `docs/reports/report-java25-plus-audit.md` §BUG-2026-0113 (audit of 2026-09-05, v1.10.0
baseline). Refines BUG-2026-0069 and LIM-0002.

## Description
Two related renderings:
1. A `checkcast` is printed with its ERASED class even when the declared generic type is available: `return (Number) k.cast(...)` for `<R extends Number> R first(Class<R>)`.
2. An erased `Object`-typed right-hand side assigned into a type-variable local gets NO cast at all: `best = e.getKey();`, `bv = (Comparable) e.getValue();` where K/V are typed from the LocalVariableTypeTable.
3. Same for arrays: `T[] out = (Object[]) Array.newInstance(...)`.

Evidence (audit workspace): `probe/dec/P_Generics.java:22`, `:36-37`, `:49`.

## Technical Analysis
- The `checkcast` decode (audit cites `Converter.java:3388`) always builds `CastExpression(new ObjectType(className))` — the erasure.
- `addGenericReturnCasts` (audit cites :1147) only wraps when NO cast is already present, so an existing erased cast is left alone.
- There is no substitution of the declared LVTT/Signature type when the `checkcast` target is its erasure, and no unchecked-cast insertion for an `Object`-typed RHS flowing into a type-variable local.

**Re-verified 2026-09-07**: `addGenericReturnCasts` still exists at
`ClassFileToJavaSyntaxConverter.java:1160` and is called from :721. The audit's other line numbers are
v1.10.0 and have shifted.

### Suggested Approach
(a) If the target's generic type G erases to the `checkcast` class, render `(G)` instead.
(b) If the RHS is erased `Object` and the target is a type variable or parameterized type, insert `(G)`.
(c) Same treatment for `Array.newInstance`.

The `Optional<CAP#1>` case in `P_Lambdas.maxOf` is a PERMANENT limitation (capture variables are not
recoverable) and must not be folded into this item.
