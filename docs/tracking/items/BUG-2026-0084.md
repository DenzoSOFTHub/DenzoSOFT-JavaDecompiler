# BUG-2026-0084: wide (0xC4) instruction operands silently discarded (iinc_w, wide loads/stores)

**Type**: Bug
**Status**: RESOLVED
**Severity**: HIGH
**Created**: 2026-06-10
**Resolved**: 2026-06-10
**Cluster**: `wide-opcode-decode` (construct-matrix gap analysis, fix order #4)
**Parent/related**: NEW — umbrella BUG-2026-0080

## Description

Class of defect: decompile→recompile failure. Matrix classes affected: C_Exceptions.

- **C_Exceptions**: Silent wrong output (compiles but corrupts semantics): in tryCatchFinally the finally body 'result += 1000' vanishes from ALL three inlined copies AND the finally clause itself is dropped — decompiled method is 'try { var3 = arg0[arg1]; } catch (ArrayIndexOutOfBoundsException e) { var3 = -1; } return var3;' returning a[idx] instead of a[idx]+1000. Minimal repro: 'int m(int i){ i += 1000; i += 5; return i; }' decompiles to 'arg0 += 5; return arg0;' — the wide iinc is gone.

## Technical Analysis

### C_Exceptions (confidence: MEDIUM)

javac emits 'wide iinc' (iinc_w) when the increment exceeds Byte range (1000 > 127). The wide opcode handler in ClassFileToJavaSyntaxConverter.decodeOpcode, case 0xC4 at src/main/java/it/denzosoft/javadecompiler/service/converter/ClassFileToJavaSyntaxConverter.java:2798-2807, reads the operand bytes (u1 wideOpcode, u2 index, s2 const for iinc) and discards them — it emits no statement and has no stack effect, unlike the narrow iinc case 0x84 at lines 2024-2041. All wide-form instructions (wide iinc, wide iload/lload/fload/dload/aload 0x15-0x19, wide i/l/f/d/astore 0x36-0x3A) are silently dropped. Cascade: with the iinc gone, the catch-any (finally) handler at pc 28 decodes to only [exception astore, athrow]; TryCatchReconstructor.removeInitialExceptionStore plus filterFinallyBody (TryCatchReconstructor.java:790-822, which strips the trailing ThrowStatement at 807-812) leave an EMPTY body, so wrapWithTryCatch line 260-262 never sets finallyBody and the finally clause is omitted entirely. Bytecode confirmed via javap: iinc_w 3,1000 at pcs 6, 19, 30 with exception table entries (2,6)->15 AIOOBE and (2,6)/(15,19)/(28,30)->28 any. [CORRECTED: The decode fix is necessary but not sufficient. Two changes are required: (1) the proposed case 0xC4 fix in ClassFileToJavaSyntaxConverter.decodeOpcode (emit iinc for wide iinc, delegate wide loads/stores) — verified to fix the standalone minimal repro; (2) fix TryCatchReconstructor.filterFinallyBody (lines 790-822): the startIdx=1 heuristic at 797-805 must not strip the first statement as an exception store when removeInitialExceptionStore (called earlier at line 227) has already removed it — e.g. only skip the first statement if it actually assigns the handler's exception variable/slot, or drop the heuristic from this call path. With both fixes, the handler body [var3 += 1000] survives, finallyBody is set (260-262), and the dedup at 268-288 then strips the catch-path inlined copy, restoring 'try {...} catch {...} finally { var3 += 1000; } return var3;'.]

### Suggested Approach

ClassFileToJavaSyntaxConverter.decodeOpcode case 0xC4 (:2798-2807) reads and drops the operands — any 'i += 1000' vanishes from output. Fix: extract emitIinc(varIdx, incr) from case 0x84 and call it for wideOpcode==0x84 with u2 index / s2 const; delegate wide loads (0x15-0x19) and stores (0x36-0x3A) to the existing pushLocal/storeLocal paths. Verified necessary-but-not-sufficient for C_Exceptions.tryCatchFinally — pairs with the finally-dedup cluster's filterFinallyBody fix. Add the minimal repro 'int m(int i){ i += 1000; ... }' as a test.

Per-finding fix details:

- In ClassFileToJavaSyntaxConverter.decodeOpcode case 0xC4 (line 2798): extract the iinc statement-emission logic from case 0x84 (lines 2024-2041) into a helper emitIinc(int varIdx, int incr, ...) and call it for wideOpcode==0x84 with the u2 index and s2 const; for wide loads (0x15-0x19) and stores (0x36-0x3A) read the u2 index and delegate to the same loadLocal/storeLocal paths the narrow opcodes use. Traced post-fix behavior on this class: the catch-path inlined copy is already stripped by removeDuplicatedFinally (TryCatchReconstructor.java:872-895), the try-path inlined copy at pc 6 (line 20) falls inside the handler line range and is dropped at TryCatchReconstructor.java:151-153, and the finally clause reconstructs from the now non-empty handler body — so this single decode fix fully restores tryCatchFinally.

## Solution Implemented

`ClassFileToJavaSyntaxConverter.decodeOpcode` case 0xC4 now decodes the wide forms instead of
reading and discarding their operands, exactly per the suggested approach:

- `wide iinc` (0x84, u2 index + s2 const) delegates to the shared `decodeIinc` helper extracted
  for BUG-2026-0082, so `i += 1000` is emitted again AND wide post/pre-increments get the same
  value-semantics handling as the narrow form.
- wide loads 0x15-0x19 (u2 index) delegate to the existing `pushLocal` path with the proper
  primitive/object type, identical to the narrow opcodes.
- wide stores 0x36-0x3A (u2 index) delegate to the existing `storeLocal` path.
- `wide ret` (0xA9) and any unknown modified opcode read the u2 operand to keep the reader
  aligned (previous behavior, now explicit).

**Residual (tracked elsewhere, as predicted by the corrected analysis)**: this decode fix is
necessary but not sufficient for C_Exceptions.tryCatchFinally. With the fix, the finally clause
reconstructs (`finally { var3 += 1000; }` now present, try-path inlined copy absorbed), but the
catch-path inlined copy is still NOT stripped (`catch (...) { var3 = -1; var3 += 1000; }`), so
the catch path still over-adds until the `TryCatchReconstructor.filterFinallyBody`/dedup fix
from the finally-dedup cluster (BUG-2026-0091, separate work stream) lands. The standalone
minimal repro is fully fixed.
