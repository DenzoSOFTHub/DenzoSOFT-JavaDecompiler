# BUG-2026-0130: try-with-resources silently flattened to open/use/close (no `try` at all)

**Type**: Bug
**Status**: IN_ANALYSIS (attempt 1 implemented, measured and reverted - see the bottom of this file)
**Severity**: CRITICAL
**Created**: 2026-09-07

**Source**: `docs/reports/report-java25-and-beyond-analysis.md` section 2, Q2. Supersedes the
"multi-resource" framing of BUG-2026-0111 (index: HIGH) and overlaps BUG-2026-0126 and the residue of
BUG-2026-0100. Where the sources disagree the more critical reading wins (CLAUDE.md): the report rates
this CRITICAL, BUG-2026-0111 rates its narrower slice HIGH -> **CRITICAL**.

## Description

A try-with-resources statement whose reconstruction fails is not emitted as a degraded `try`; the
whole exception group is **dropped** and the raw linear statements are printed. The result is
`open(); use(); close();` with no `try` and no handler, so the resource is not closed when the body
throws. The output compiles, so no gate reports it.

```java
static void h_void_StringReader(String s, StringBuilder sb) throws IOException {
    StringReader r = new StringReader(s);
    sb.append((char) r.read());
    r.close();                                   // not executed if read() throws
}
```

Runtime proof (`SCRATCH/rt/R_Twr.java`, `-g`): the original prints `closed=1`, the recompiled
decompilation prints `closed=0`.

Measured reconstruction rate, probe `P_Twr2` (9 TWR shapes each written on ONE source line) and
`P_Twr3` (the same shapes spread over several lines):

| javac mode | P_Twr2 (one line) | P_Twr3 (multi-line) |
|---|---|---|
| `-g:source,lines` | 0 / 9 | 8 / 9 |
| `-g` | 0 / 9 | 8 / 9 |
| `-g:none` | 2 / 9 | 2 / 9 |

`java.base` emits 22 `try (` in 18 files.

## Technical Analysis

Two independent causes, both around `TryCatchReconstructor.applyGroup`:

1. **The group is deleted.** With line information, statements are classified into
   before/try/after by `sLine in [tryStartLine, tryEndLine]` (:395). A one-line TWR puts the resource
   init, the body, the inlined `close()` and the `return` on the same line, so everything lands in
   the try body; the group then looks like the TWR compiler pattern with a trivial body and
   `isTryBodyTrivial(tryBody) && isTryWithResourcesPattern(...)` (:586) does
   `return null; // skip this exception group - emit original statements unchanged`. The handler is
   discarded silently. The same branch fires at `-g:none` for pc-classified groups whose body is
   only a declaration.
2. **`ModernTwrReconstructor` is tuned to the line-based shape** (BUG-2026-0122 notes) and does not
   match the pc-grouped shape, which is why `-g:none` stays at 2/9 even when the grouping is right.

### Suggested Approach

- Never drop a group whose handler is the TWR desugar. Replace the `return null` at :586 with a
  reconstruction attempt; if the attempt fails, emit the desugared
  `try { ... } catch (Throwable t) { r.close(); throw t; }` (correct, compilable, ugly) and record a
  `TWR_UNRECONSTRUCTED` diagnostic.
- Classify TWR groups by bytecode pc even when lines exist, restricted to groups whose handler type
  is `Throwable` and whose handler body reaches `addSuppressed`/`close()`.
- Make `ModernTwrReconstructor` match on structure rather than on which list the pieces landed in.

### What NOT to try

Enabling `usePc100` for all line-bearing groups. It was tried in BUG-2026-0122: -756 `catch (` across
`java.base` and at least one real handler lost (`SunEC$ProviderService`).

### Affected Modules

- `service/converter/transform/TryCatchReconstructor.java`
- `service/converter/transform/ModernTwrReconstructor.java`

### Estimated Effort

MEDIUM-HIGH.

## Attempt 1 (2026-09-07/08): root cause corrected, fix built and runtime-verified, REVERTED with BUG-2026-0131

### The report's root cause #1 is wrong; the real one is BUG-2026-0131

The report attributed the `-g` / `-g:source,lines` flattening of a ONE-LINE try-with-resources to
"everything is on the same line, so the whole desugar lands in the try body, the body then looks
trivial and `applyGroup` returns null at :586". Instrumenting `applyGroup` on `P_Twr2` shows
something different:

```
[applyGroup] try=[9,14) lines=[3,3] usePc=false trivial=true twrPat=true catches=1 fin=false
   TRY  VariableDeclarationStatement line=3
   AFT  VariableDeclarationStatement line=0     <- int var2 = in.read();
   AFT  ExpressionStatement          line=0     <- in.close();
   AFT  ReturnStatement              line=0     <- return var2;
```

`javap -l` confirms it: a one-line TWR method has a LineNumberTable with a SINGLE entry (`line 3: 0`),
so only the resource declaration carries a line and every statement after it has `line == 0`. Those
statements are pushed past the handler by the line branch — i.e. this is exactly BUG-2026-0131, and
the try body is left holding only the declaration, which is why the trivial-body test at :586 then
fires. **BUG-2026-0130 cannot be fixed before BUG-2026-0131.**

### Runtime evidence gathered (A/B oracle: original run vs recompiled decompilation run)

Fixtures in `SCRATCH/w3`, runner `SCRATCH/ab.sh` (`CLASSES=<build>`):

| fixture | shape | baseline `-g` | with 0131+0130 |
|---|---|---|---|
| `RTwrB` | TWR + `catch` + `finally` | compiles, **exception escapes uncaught** | PASS (3 modes) |
| `RTwrA` | TWR plain / +catch / +finally | compiles, resource never closed on throw | PASS (3 modes) |
| `RTwrOneLine` | one-line TWR, body throws | 3 divergences incl. an uncaught escape | 2 divergences left |
| `RTwrM` | multi / nested / loop TWR | `twrThrow` escapes uncaught | `twrThrow` fixed; `nested()` opens the two resources in the wrong order |

The baseline output in every failing row RECOMPILES CLEANLY — this is the silent class, and no
recompile gate can see it.

### The fix that was built (and is ready to re-apply on top of 0131)

1. `ModernTwrReconstructor`: a resource declaration split by the decode into `R r = null;` before the
   region + `r = new R();` as the first body statement passed the existing checks and produced
   `try (R r = null) { r = new R(); ... }` — which does not compile
   ("auto-closeable resource r may not be assigned"). Fold the assignment into the header; decline
   (leave the raw desugar) when the shape is not exactly that, and never fold `r = null` itself.
2. `TryCatchReconstructor` LIM-0008 path: when a resource's initializer cannot be recovered, emit the
   raw desugar (`try { } catch (Throwable t) { r.close(); throw t; }`) instead of a
   `try (R r = null)` header that claims a resource that is never opened.

Both are written and were verified to turn `RTwrA`/`RTwrB` from silently wrong into A/B-identical in
all three debug modes. They were reverted together with BUG-2026-0131 because without it they have no
effect, and with it the corpus regressions recorded in 0131 apply.

### What remains after that

`try (R r = new R()) { return r.use(); }` — the body-`return` variant — is still flattened even with
both changes (`ModernTwrReconstructor` does not match it). `RTwrOneLine.a`/`c` still lose the close on
the exception path. Nested TWR (`RTwrM.nested`) still emits the two resource opens in the wrong order.
The per-shape counts on the report's probes with 0131+0130 applied were: `P_Twr2` 0/9 -> 2/9,
`P_Twr3` 8/9 -> 8/9, `P_Twr` 0/10 -> 1/10 at `-g`; the runtime oracle, not these counts, is the
measure that matters.
