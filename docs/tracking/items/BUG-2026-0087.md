# BUG-2026-0087: dup+istore leaves side-effecting call aliased on stack — stream read() duplicated

**Type**: Bug
**Status**: IN_ANALYSIS
**Severity**: HIGH
**Created**: 2026-06-10
**Cluster**: `dup-store-alias` (construct-matrix gap analysis, fix order #7)
**Parent/related**: NEW — umbrella BUG-2026-0080

## Description

Class of defect: decompile→recompile failure. Matrix classes affected: C_Java7TryResources.


## Technical Analysis

### C_Java7TryResources (confidence: HIGH)

**Symptom**: Wrong output (compiles, wrong semantics) in copy(): original `while ((b = in.read()) != -1) { out.write(b); }` is decompiled as `int var3 = var1.read(); while (var1.read() != -1) { var2.write(var3); }` — the stream is read once before the loop and re-read in the condition, and the stale first byte is written repeatedly instead of each read byte.

The bytecode is `17: aload_1; 18: invokevirtual read; 21: dup; 22: istore_3; 23: iconst_m1; 24: if_icmpeq 35` (assignment inside loop condition). The `dup` handler (src/main/java/it/denzosoft/javadecompiler/service/converter/ClassFileToJavaSyntaxConverter.java:1931-1933) pushes `stack.peek()` — an alias of the raw `var1.read()` MethodInvocationExpression. `istore_3` then calls storeLocal (ClassFileToJavaSyntaxConverter.java:2884-2944) which pops one copy and emits `int var3 = var1.read();` as a standalone statement in the loop-header block, leaving the OTHER alias of the side-effecting call on the stack; if_icmpeq consumes it, so the loop condition becomes `var1.read() != -1` instead of referencing var3. StructuredFlowBuilder's while-pattern already has an assignment-into-condition merge (BUG-2026-0016, src/main/java/it/denzosoft/javadecompiler/service/converter/cfg/StructuredFlowBuilder.java:705-751) that would produce `while ((var3 = var1.read()) != -1)`, but its gate `conditionUsesVariable(condition, assignedVarName)` (:740) fails because the condition contains the duplicated call, not the variable — so the header statements are emitted once before the loop (:749) and the condition keeps a second read() call.

**Fix detail**: In ClassFileToJavaSyntaxConverter.storeLocal, after `Expression value = popOrUnderflowRef(stack);` (:2903), detect the dup alias: `if (!stack.isEmpty() && stack.peek() == value) { stack.pop(); stack.push(new LocalVariableExpression(line, type, name, index)); }`. This makes the loop condition `var3 != -1`, which then satisfies the existing conditionUsesVariable gate at StructuredFlowBuilder.java:740, so the BUG-2026-0016 merge rewrites it to `while ((var3 = var1.read()) != -1)` with a hoisted bare `int var3;` declaration — restoring both side-effect count and value flow. The reference-identity check keeps the change targeted: `new;dup;invokespecial;astore` and `iload;dup;iadd` idioms leave no alias on the stack at store time, and `i = j = k` chains degrade gracefully to `j = k; i = j;`.


### Suggested Approach

In ClassFileToJavaSyntaxConverter.storeLocal, after popping the value (:2903): if stack.peek() == value (reference identity, the dup twin), pop it and push a LocalVariableExpression for the stored slot. The loop condition then becomes 'var3 != -1', which satisfies the existing BUG-2026-0016 assignment-into-condition merge gate (StructuredFlowBuilder.java:740), yielding 'while ((var3 = var1.read()) != -1)' — restoring side-effect count. Identity check keeps new/dup/invokespecial and iload/dup/iadd idioms untouched; 'i = j = k' degrades gracefully to two statements.
