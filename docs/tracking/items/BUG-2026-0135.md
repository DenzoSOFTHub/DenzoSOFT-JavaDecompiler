# BUG-2026-0135: A try/finally is split into several try/finally blocks, each re-running the finally

**Type**: Bug
**Status**: TO_ANALYZE
**Severity**: HIGH
**Created**: 2026-09-07

**Found while**: verifying BUG-2026-0129 (Q1) with the runtime A/B oracle. It is a DIFFERENT root
cause from 0129 and is deliberately not silenced by that fix.

## Description

javac protects a `try { ... } finally { ... }` with a single `any` handler but SEVERAL protected
ranges — one per stretch of try code between the inlined finally copies. The reconstructor turns each
range into its own `try/finally`, so the finally body executes once per fragment instead of once per
entry.

Runtime proof (SCRATCH/w1/Q1a.java, all three debug modes; `u` counts the finally action):

```java
static void voidNestedReturn(int n) {          // original: u=1 on both paths
    try {
        if (n > 0) { flag = 1; return; }
        flag = 2;
    } finally { unlock(); }
}
```

decompiles (post-0129) to

```java
try {
    if (n > 0) { flag = 1; return; }
} finally { unlock(); }
try {
    flag = 2;
} finally { unlock(); }        // second execution on the fall-through path
```

`voidNestedReturn(0)`: original prints `u=1`, the recompiled decompilation prints `u=2`.

The same mechanism in a loop produces a NESTED duplicate:

```java
for (int i = 0; i < n; i++) {
    try { if (i == 2) { continue; } acc += i; } finally { unlock(); }
}
```

becomes `try { if (i==2) { unlock(); } else { try { acc += i; } finally { unlock(); } } } finally {
unlock(); }` — original `u=5`, decompiled `u=10`. This form appears at `-g` and `-g:source,lines`;
`-g:none` is correct for it.

## Technical Analysis

`TryCatchReconstructor` groups by exception-table ENTRY. A try/finally with an early exit has one
`any` target but multiple `from/to` ranges (`NativeLibraries.loadLibrary`: `[57,81) [88,193)
[200,266) [273,356)` all targeting 363). Each range becomes its own group and therefore its own
`try/finally`.

### Suggested Approach

Merge exception-table entries that share the same handler pc AND the same catch type into ONE group
covering the union of the ranges, before classification. The statements sitting in the gaps between
the ranges are the inlined finally copies BUG-2026-0129 now removes, so after 0129 the union is
contiguous in statement order.

### Affected Modules

- `src/main/java/it/denzosoft/javadecompiler/service/converter/transform/TryCatchReconstructor.java`

### Estimated Effort

MEDIUM. Risk: merging ranges that a `catch` genuinely splits (a handler shared by two disjoint tries
in the same method), so the merge must also require the ranges to be separated only by statements the
dedup identified as finally copies.
