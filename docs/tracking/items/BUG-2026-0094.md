# BUG-2026-0094: Present Signature attributes never consulted: implements/extends clauses and record components erased

**Type**: Bug
**Status**: IN_ANALYSIS
**Severity**: MEDIUM
**Created**: 2026-06-10
**Cluster**: `signature-unread` (construct-matrix gap analysis, fix order #14)
**Parent/related**: NEW — umbrella BUG-2026-0080

## Description

Class of defect: decompile→recompile failure. Matrix classes affected: C_RecursiveGenerics, C_RecordPattern.


## Technical Analysis

### C_RecordPattern (confidence: HIGH)

**Symptom**: Latent wrong output (compiles in this class only by luck, no javac error here): generic record component erased — decompiled `public static final record Box<T>(Object value)` vs original `record Box<T>(T value)`; correspondingly `unbox` emits a raw pattern `o instanceof C_RecordPattern.Box(Object var3)` instead of `Box<?>(Object v)`. Round-trip source mismatch; any external caller of Box.value() relying on T would mis-compile.

ClassFileToJavaSyntaxConverter.java:156-164 builds the record header components from the Record attribute using only the erased descriptor: `new JavaSyntaxResult.RecordComponentInfo(rc.name, rc.descriptor, parseType(rc.descriptor))` (:160-161). The per-component Signature attribute (`TT;` — verified present in C_RecordPattern$Box.class via javap, and emitted by javac regardless of -g) sits unread in RecordAttribute.RecordComponent.attributes (RecordAttribute.java:20-28). The class-level Signature IS read (:150-153) for the `<T>` type parameter, which is why the output is the inconsistent `Box<T>(Object value)`.

**Fix detail**: In the record-component loop at ClassFileToJavaSyntaxConverter.java:159-162, scan rc.attributes for a SignatureAttribute and, when present, parse it with parseSignatureType and use that Type (and the signature string) for the RecordComponentInfo instead of parseType(rc.descriptor); extend JavaSyntaxResult.RecordComponentInfo with the signature-derived type and make JavaSourceWriter's record-header emission use it. This restores `T value` (and parameterized component types like List<String> generally). Separately/cosmetically, the instanceof record pattern for a generic record could emit `Box<?>(...)` — javac accepts the raw form (verified), so that part is optional.

### C_RecursiveGenerics (confidence: HIGH)

**Symptom**: 2 javac errors: "Box is not abstract and does not override abstract method set(Object) in Container" (dec line 13) and "name clash: set(E) in Box and set(Object) in Container have the same erasure, yet neither overrides the other" (dec line 23). Cause text in output: `public static class Box<E> implements C_RecursiveGenerics.Container {` — raw Container instead of Container<E>.

JavaSourceWriter emits the implements clause from the erased constant-pool interface names and never consults the class Signature attribute's superinterface section. Inner-class path: src/main/java/it/denzosoft/javadecompiler/service/writer/JavaSourceWriter.java:753-764 iterates `inner.getInterfaces()` (erased internal names like `C_RecursiveGenerics$Container`) and calls emitRef with simpleNameFromInternal — no type arguments. The identical defect exists in the top-level path at JavaSourceWriter.java:408-419, and the extends clause has the same gap (writer:398-406 and 742-751 emit raw superName). Crucially the data is NOT missing: javap on /tmp/matrix/cls/C_RecursiveGenerics$Box.class shows the class Signature attribute `<E:Ljava/lang/Object;>Ljava/lang/Object;LC_RecursiveGenerics$Container<TE;>;` is emitted even without -g (Signature attributes are not debug info). The writer already uses this signature for the type-parameter list `<E>` via SignatureParser.parseClassTypeParameters (writer:721-726 / 377-382) but ignores the rest. A ready-made parser exists: SignatureParser.parseClassInterfaceTypes at src/main/java/it/denzosoft/javadecompiler/util/SignatureParser.java:55 (and parseClassSuperType at :42) — they are simply never called from the writer. This refutes the 'erasure-generics / no-LVTT data loss' hypothesis for this class: it is unused-signature, not missing-signature.

**Fix detail**: In JavaSourceWriter, in both class-header emitters (top-level ~lines 398-419 and inner ~lines 742-764): when result.getSignature()/inner.getSignature() is non-null, call SignatureParser.parseClassInterfaceTypes(signature) and SignatureParser.parseClassSuperType(signature); if they return entries, emit those parameterized type strings (e.g. `Container<E>`) for the implements/extends clauses instead of (or appended to) the erased emitRef output, falling back to the current getInterfaces()/getSuperName() path when the signature is absent or the parser returns null/empty. To preserve emitRef hyperlinking, emit the base reference via emitRef using the erased internal name and then printText only the `<...>` type-argument suffix extracted from the parsed string. Verify parseClassInterfaceTypes handles nested names (Container is `C_RecursiveGenerics$Container` in the signature) and `$`->`.` conversion. Verified: changing the line to `implements C_RecursiveGenerics.Container<E>` resolves both javac errors.


### Suggested Approach

Not a -g limitation — the data exists. (1) JavaSourceWriter class-header emitters (top-level :398-419, inner :742-764) emit erased getInterfaces()/getSuperName(); call the existing-but-unused SignatureParser.parseClassInterfaceTypes (:55) / parseClassSuperType (:42) on the class Signature and print the parameterized forms ('implements Container<E>'), falling back when absent. Fixes both C_RecursiveGenerics Box errors. (2) ClassFileToJavaSyntaxConverter record-component loop (:159-162): read the per-component Signature from RecordAttribute.RecordComponent.attributes (RecordAttribute.java:23) instead of the erased descriptor, restoring 'record Box<T>(T value)' (C_RecordPattern latent divergence).
