# BUG-2026-0121: Trailing return lost when a synchronized block sits inside an if with following statements

**Type**: Bug
**Status**: TO_ANALYZE
**Severity**: HIGH
**Created**: 2026-09-05

## Description
For the shape `if (f) { synchronized (l) { ... } stmt; } return x;` the method's trailing `return` is dropped and the if/else is inverted, so the output does not compile (missing return statement). Pre-existing: reproduced on the v1.10.0 build, where the same method additionally lost the lock (BUG-2026-0101). Discovered while verifying the BUG-2026-0101 fix.

## Technical Analysis
Reproducer `S_Sync2.ifSyncThenStmt`. The monitor region's synthetic try/finally interacts with the structured-flow reconstruction of the enclosing `if`: the merge point after the handler is mis-identified, the else-branch absorbs the tail `return`, and the statement that follows the if is emitted after it with no terminator. Same family as BUG-2026-0122 (region boundaries decided on source lines).

### Suggested Approach
Re-check after BUG-2026-0122: classifying the region by bytecode pc rather than by line is expected to fix the merge point. If it does not, handle the monitor try/finally merge point explicitly in the flow builder.
