# BUG-2026-0116: import of the outer class lost for nested generic type arguments

**Type**: Bug
**Status**: IN_ANALYSIS
**Severity**: MEDIUM
**Created**: 2026-09-05
**Source**: `docs/reports/report-java25-plus-audit.md` §BUG-2026-0116 (audit of 2026-09-05, v1.10.0
baseline).

## Note on severity
The audit rated this LOW-MEDIUM, the original index row LOW. Resolved to **MEDIUM** per the project
rule: where two sources disagree on severity, the more critical one stands. It is also the right call
on the evidence — this is a recompile FAILURE, reproduced today in the `-g` construct matrix.

## Description
A declaration whose GENERIC signature names a nested type gets no import for the outer class, so the
output does not compile:

```java
ArrayList<Map.Entry<String, Integer>> entries = ...;   // no `import java.util.Map;`
```

Evidence: `C_VarInference` in the construct matrix at `-g` — audit reference `mx_g/dec/C_VarInference.java:68`.

**Re-verified 2026-09-07**: `C_VarInference` still fails the `-g` round trip with
`package Map does not exist`. It is one of the two known `-g` failures in the current 53/55 baseline
(the other is `C_RecordPattern`, BUG-2026-0107 territory).

## Technical Analysis
`JavaSourceWriter.collectStatementImports` imports `vds.getType()` — the ERASED type — but never runs
`collectSignatureImports` on `vds.getGenericSignature()`, and it is the generic signature that
actually gets printed.

**Re-verified 2026-09-07**: `collectStatementImports` still calls only
`addTypeImport(imports, vds.getType(), thisPackage)`. `collectSignatureImports` exists at
`JavaSourceWriter.java:1774` and is applied to class, field and method signatures (:1499, :1515,
:1537) — but not to statement-level declarations.

### Suggested Approach
Call `collectSignatureImports` for declaration generic signatures, and for the same reason for
`LambdaExpression.getInterfaceGenericSignature` and for-each element signatures.
