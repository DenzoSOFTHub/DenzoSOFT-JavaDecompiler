# IMP-2026-0072: retire the JD flow pipeline

**Type**: Improvement
**Status**: IN_PROGRESS
**Severity**: HIGH
**Created**: 2026-09-05 (filed by the Java 25+ audit as the open "dual pipeline decision"; the decision itself was taken 2026-09-07)
**Source**: `docs/reports/report-java25-and-beyond-analysis.md` §3. Resolves the invest-or-retire
decision left open in ROADMAP §3. **Approved by the project owner on 2026-09-07.**
**Related**: IMP-2026-0074 (single transform pipeline) becomes a one-call refactor once this lands;
BUG-2026-0128 is step 2 of the recipe below.

## Description
The ported JD pipeline (`service/converter/cfg/jd/`, ~3,800 lines) is to be removed. Measured against
the legacy builder it loses control flow outright: with `-Ddenzo.jd.pipeline=true` a `for` loop is
emitted as a single `if`/`else return` with the back-edge dropped, which COMPILES in a `void` method
and is silently wrong. Matrix 36/55 in all three debug modes against legacy's 55/53/55; `java.base`
emits 19 `while (` and 8 `for (` against legacy's 4,707 and 2,819.

Its only live contribution is the selective route (active with the flag OFF) that folds
record-deconstruction switches via `TypeSwitchRecordFolder`.

## Technical Analysis

### What the selective route actually gets right — MEASURED 2026-09-07, not assumed
A freeze fixture (`src/test/resources/jd-freeze/JdFreeze.java`, four shapes, compiled `-g` with JDK 25)
was decompiled with the v1.13.0 build and recompiled. Result:

| Shape | Decompiles to | Recompiles |
|---|---|---|
| `return switch` + flat deconstruction + `default` | correct `case Circle(Point p, int r) -> ...` | **yes** |
| `return switch` + unnamed component (`Point _`) | correct | **yes** |
| `return switch` + sealed exhaustive, no `default` | correct arms, but a hoisted `Point a;` collides with the arm bindings | **NO** — `variable a is already defined` |
| `return switch` + NESTED deconstruction | `while (true) { switch ... }`, raw, **no `return` at all** | **NO** |

So only TWO shapes are actually protected. This corrects the report on two points:
1. The report lists sealed-exhaustive and nested as things the route "gets right". Measured, both are
   already broken — they cannot regress because they do not work today.
2. The report states `C_RecordPattern` and `C_Sealed` in the construct matrix depend on the route.
   `C_Sealed.java` contains **zero** `switch` statements and cannot depend on a record-switch fold.
   `C_RecordPattern` does depend on it — and its known `-g` matrix failure is EXACTLY the hoisted-
   binding collision above (`C_RecordPattern.java:49: variable a is already defined`), i.e. one of the
   two remaining `-g` failures in the 53/55 baseline is this defect, not a separate one.

### Order of work (from the report §3, revised by the measurement above)
1. **Freeze** — DONE for the fixture and golden output; the `DecompilerTest` case is deferred, see below.
   Only the two working shapes are assertable; the two broken ones are recorded as the step-2 target.
2. **Implement the value merge** for the `typeSwitch` restart loop in the legacy builder — this is
   BUG-2026-0128 generalised, consuming arm values at any merge consumer.
3. **Route record-switch methods to legacy** behind a flag; verify against the frozen fixture, the
   three-mode matrix, and the `java.base` raw-`typeSwitch` count (must stay <= 5 and fall as step 2 lands).
4. **Delete** `cfg/jd/`, `runJdPipeline`, the JD half of the transform chain
   (`ClassFileToJavaSyntaxConverter` :1478-1600) and the per-method decode-state snapshot/restore that
   exists only for the JD fall-through.

**Do not invest in parity.** Parity means re-implementing loop reconstruction, switch break/continue
semantics, TWR and the five transforms the JD chain skips, on an engine that today loses loops.

### Affected Modules
