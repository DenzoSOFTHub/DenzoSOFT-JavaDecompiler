# BUG-2026-0131: Flow-builder-synthesised statements (`line=0`) pushed out of the try region

**Type**: Bug
**Status**: IN_ANALYSIS (attempt 1 implemented, measured and reverted - see the bottom of this file)
**Severity**: HIGH
**Created**: 2026-09-07

**Source**: `docs/reports/report-java25-and-beyond-analysis.md` section 2, Q3. A precisely delimited
slice of BUG-2026-0126 (HIGH) and the mechanism behind the `Console` half of BUG-2026-0121's family.
Both sources say HIGH.

## Description

In classes that carry line information, a loop / labelled block / merged if-else that
`StructuredFlowBuilder` synthesised carries `lineNumber == 0`. `TryCatchReconstructor.applyGroup`
classifies statements into before/try/after by line, so such a statement fails the "inside the try"
test and is appended to **afterTry** — it is emitted after the `try` statement instead of inside it.
Exception coverage is silently removed, and in the worst shapes the method tail is lost as well.

```java
// source                                    // output (-g)
try {                                        try {
    for (int i = 0; i < a.length; i++) {         int i = 0;
        if (a[i] < 0) { r = i; break; }      } catch (RuntimeException e) {
    }                                        }
} catch (RuntimeException e) { }             outer: while (i < a.length) { ... }   // outside
```

`java/io/Console.instantiateConsole` additionally loses `c = new ProxyingConsole(jc)` and everything
after the try. When the loop is a for-each, the hoisted iterator gets the catch variable's slot type
(`IllegalStateException e = xs.iterator();`) and the file no longer compiles; the `int i` /
`Iterator var2 = null` forms compile and silently drop the exception coverage.

Scale (measured, `java.base`, `-g`): strict scanner `SCRATCH/loopaftertry.py` reports **59 sites in
41 files** (`Console:597`, `ProcessBuilder:1227`, `Inet6Address:700`, `Charset:415`, `JarFile:722`,
`JceSecurity:347`, `SubmissionPublisher` x5, `PriorityBlockingQueue` x2, ...). At `-g:none` the same
fixture is correct, because the pc-based classification is used there.

## Technical Analysis

`TryCatchReconstructor.applyGroup` :395-412: when the class has lines (`usePc100 == false`) a
statement with `line == 0` fails the `sLine > 0 && sLine >= tryStartLine && sLine <= tryEndLine`
test, is not `beforeTry` (a try statement has already been seen), and falls through to the final
`afterTry.add(s)`. `minPcOf(s)` (:91-131) already descends into compound bodies and returns the right
pc — for the probe it returns 17, inside the group range `[2,27)` — but it is consulted only when
`usePc100` is true. BUG-2026-0125's "an unpositioned statement inherits its predecessor's
classification" rule is likewise gated on `usePc100`.

Traced with an instrumented `applyGroup` on `P_TryTail` (`-g`):

```
[applyGroup] try=[2,27) lines=[26,26] usePc=false
[stmt] VariableDeclarationStatement line=26 pc=3      -> tryBody
[stmt] LabelStatement                line=0  pc=17    -> afterTry
```

### Suggested Approach

In the line branch, classify `sLine <= 0` statements with `minPcOf(s)` against the group's pc union
(the `inAnyRange122` computation that already sits two lines above), falling back to the predecessor
rule. This touches only statements that today carry NO position information, so it cannot move a
line-positioned statement and cannot reopen the `SunEC$ProviderService` handler loss that killed the
wholesale pc switch in BUG-2026-0122.

### Affected Modules

- `service/converter/transform/TryCatchReconstructor.java`

### Estimated Effort

LOW.

## Attempt 1 (2026-09-07/08): implemented, measured, REVERTED

The report's approach was implemented exactly as proposed and measured against the baseline build.
It fixes the defect it targets and is a large net win on the displacement metrics, but it
destabilises two neighbouring reconstructions that the report did not anticipate. It was reverted;
the working tree carries none of it. **The numbers below are the reason to try again, and the
blocker below is what the next attempt has to solve first.**

### What was implemented

In `TryCatchReconstructor.applyGroup`, in the LINE branch (`usePc100 == false`), a statement with
`sLine <= 0` was positioned by `minPcOf(s)` against the union of the group's protected ranges:
inside -> `tryBody`; before the group's lowest `startPc` -> `beforeTry`; otherwise left to the
existing logic. Roughly 25 lines, no other file touched.

### What it fixed (measured)

| metric | baseline | with the change |
|---|---|---|
| `SCRATCH/loopaftertry.py` sites / files (java.base) | 59 / 41 | **4 / 4** |
| `catch (` in java.base (exception coverage) | 3,740 | **3,759** |
| `finally` / `try (` | 1,751 / 22 | 1,753 / 24 |
| batch errors | 0 / 3,376 | 0 / 3,376 |
| construct matrix (3 modes) | 55 / 53 / 55 | 55 / 53 / 55 (unchanged) |

Read against the original source (rung 1), the repaired files are unambiguous.
`jdk/internal/util/xml/PropertiesDefaultHandler.store` went from a `while (var7.hasNext())` loop
stranded AFTER the try (unreachable, `var7` out of scope) to the source's own
`for (Map.Entry e : props.entrySet())` inside the try; `jdk/internal/vm/VMSupport.encodeAnnotations`
became character-for-character the JDK source including its `try (DataOutputStream dos = ...)`.
A `TryLoopPos` fixture (`for` + `break` inside a `try/catch`) goes from output that does not compile
(`i` out of scope, loop outside the try) to output identical to the source.

### Why it was reverted

1. **`testNestedSync` (an existing committed test) fails.** For an `any`-only group — a `finally`,
   or the synchronized desugar — the group being applied IS the monitor's own entry. Pulling the
   line-0 statements in wraps the already-reconstructed `synchronized` in a redundant
   `try { } finally { /* __MONITOREXIT__ */ }` (marker leaked into the output) and moves the loop's
   `iinc` INSIDE the lock:

   ```java
   // source                                     // with the change
   for (int i = 0; i < n; i++) {                 int i = 0;
       synchronized (this) { counter += i; }     while (i < n) {
   }                                                 synchronized (this) { counter += i; i++; }
                                                 }
   ```

   Restricting the branch to groups with a TYPED handler removes this regression completely
   (`__MONITOREXIT__` gone, the `for` restored) — but then the try-with-resources shapes split
   between typed (the `Throwable` desugar) and untyped (the user `finally`) groups and
   `RTwrOneLine` stops recompiling (`cannot find symbol var2`). Excluding only
   `SynchronizedStatement`, or requiring both `minPcOf` and a new `maxPcOf` to fall inside the same
   range, does not fix it either (both were tried).

2. **Two files lose statements.** With the "absent invoked method names" census (iterator idioms
   excluded, since for-each reconstruction legitimately removes `iterator`/`hasNext`/`next`), the
   corpus goes 638 -> 644 absent names, all of it in `jdk/internal/foreign/abi/UpcallLinker` (+5;
   one displaced loop is recovered, a second is dropped entirely) and `java/nio/file/Files` (+1;
   `mismatch` collapses to `throw totalRead;`). Losing statements is the gravest defect class here,
   so this needs an answer even though 3,374 of 3,376 classes are unaffected or improved.
